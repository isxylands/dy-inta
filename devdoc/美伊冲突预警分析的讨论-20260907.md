# 二、真正应该搜集的不是“新闻”，而是 10 类信号

可以把它理解成：

**政治意图 + 军事能力 + 军事准备 + 实际行动 + 民用系统异常 + 第三方避险行为 + 物理证据 + 经济反馈**

必须同时看。

### 1. 政治与战略意图信号

监测美国总统、白宫、国防部、CENTCOM、国务院，以及伊朗最高国家安全委员会、IRGC、外交部、议会、最高领袖体系的讲话。

但重点不是简单做 NLP 情感分析，而是提取：

**威胁对象、行动条件、红线、时间窗口、措辞强度变化、报复承诺和降级条件。**

例如：

> “如果再次攻击美国舰艇，将……”

和

> “我们保留回应权利”

预警意义完全不同。

更重要的是观察：

**措辞 + 军事行动是否一致。**

目前伊朗已经公开警告进一步攻击将得到“更快、更重、更痛苦”的回应，因此这种表态必须与后续物理信号联合监测。([Reuters](https://www.reuters.com/world/middle-east/iran-tackle-economic-issues-says-further-attacks-will-be-more-painful-2026-09-06/?utm_source=chatgpt.com))

# 三、军事态势不要只看“某架飞机在哪里”，而要看“模式变化”

ADS-B、卫星影像、官方图片、NOTAM 等真正适合预警的，是**态势异常检测**。

例如正常状态可能是：

> A → A → A → A → A

突然出现：

> A → A → B → B → C

这个“状态转移”才重要。

因此应关注聚合性指标：

| 信号               | 可能意味着什么      |
| ---------------- | ------------ |
| 区域军机活动强度明显增加     | 战备水平提高       |
| 加油机、预警机等支援活动明显增加 | 可能支持更大规模空中行动 |
| 民航航路大面积绕飞        | 风险已经被专业机构感知  |
| 军事基地飞机明显分散       | 防范先发攻击       |
| 防空阵地状态变化         | 防御准备加强       |
| 海军舰艇活动模式变化       | 海上行动准备       |
| 后勤运输突然增加         | 持续行动能力建设     |
| 医疗、搜救、补给活动加强     | 风险预备措施       |

这里有个非常重要的经验：

> **攻击行动本身未必是最好的预警信号，攻击发生之前的后勤、防护和民用避险行为往往更早。**

# 四、民航其实是一个非常优秀的“战争传感器”

这一类我会给予很高权重。

监测：

**NOTAM、FIR 限制、EASA CZIB、航空公司取消航班、航路绕飞、机场关闭、GPS 干扰报告。**

截至目前，EASA 对：

**伊朗、伊拉克、波斯湾和阿曼湾**

仍维持冲突区域风险警告。

例如针对波斯湾和阿曼湾的最新 CZIB 明确指出，美伊冲突、针对商船的反复攻击以及美军行动已经使巴林、科威特、卡塔尔、阿联酋及部分阿曼湾上空产生较高风险。([EASA](https://www.easa.europa.eu/en/domains/air-operations/czibs?utm_source=chatgpt.com))

这类信息有一个巨大优势：

政府讲话可能有宣传目的，

但：

> **航空公司真的会不会让一架载着 300 人的客机飞过去，是一种“用真金白银投票”的风险判断。**

所以它往往比社交媒体情绪可靠得多。

# 五、AIS + 海事情报，是现在最重要的一组信号

霍尔木兹尤其适合做这种分析。

不能只看：

> “某艘船 AIS 消失了。”

因为关 AIS、信号遮挡、卫星覆盖问题都可能造成假象。

真正有价值的是观察**群体统计特征**：

| 指标            | 预警意义        |
| ------------- | ----------- |
| 每日穿越霍尔木兹船数    | 是否正在形成事实封锁  |
| VLCC/LNG 船通过率 | 能源运输影响      |
| 等待区船舶数量       | 是否出现拥堵/不敢通行 |
| 船舶掉头比例        | 风险感知突然恶化    |
| AIS Dark 异常增长 | 规避/干扰/军事风险  |
| 航速异常          | 安全航行模式变化    |
| 航路整体偏移        | 危险区出现       |
| 港口装卸下降        | 制裁或军事影响     |
| 战争险保费         | 商业风险定价      |
| 船东暂停航行公告      | 私营部门风险判断    |

现在已经出现一个非常明显的例子：过去 10 天霍尔木兹商品船日均通行量约降至 **10 艘**，9 月 5 日一度只有 **2 艘**。([Reuters](https://www.reuters.com/world/middle-east/hormuz-traffic-dips-lowest-since-may-after-us-iranian-strikes-ships-2026-09-06/?utm_source=chatgpt.com))

这类**行为数据**的预警价值通常高于口头声明。

# 六、卫星影像是“物理世界裁判”

新闻说：

> “某雷达站被摧毁。”

不要马上写入“事实”。

应该建立：

**Claim → Evidence → Assessment**

例如：

> Claim：雷达站被摧毁  
> ↓  
> 官方声明  
> ↓  
> Sentinel / Planet / Maxar 等影像  
> ↓  
> SAR / 光学变化检测  
> ↓  
> 火灾/热异常  
> ↓  
> 后续维修活动  
> ↓  
> 该设施是否恢复运行

最终结论可能是：

**Confirmed / Highly Likely / Likely / Uncertain / Unlikely / False**

而不是简单：

**真 / 假。**

这对于你前面提出的“**真实到什么程度**”尤其重要。

# 七、核情报必须单独建立一套预警链

这是整个系统中战略级别最高的一条。

需要监测：

**IAEA 报告 + 商业卫星影像 + 伊朗核机构声明 + 核设施施工变化 + 电力变化 + 外交活动 + 核材料核算信息。**

当前最大的风险并不只是“伊朗有没有核武器”。

而是：

> **国际社会还能不能知道相关核材料现在在哪里、在做什么。**

目前 IAEA 对部分关键设施和核材料仍缺乏充分核查能力；近期报道显示，机构仍无法确认部分浓缩铀库存的当前状态和位置。([Reuters](https://www.reuters.com/world/europe/us-allies-want-iaea-board-report-iran-un-security-council-diplomats-say-2026-09-04/?utm_source=chatgpt.com))

因此真正应建立的指标是：

**Knowledge Gap（认知缺口）**

它本身就是预警指标。

例如：

> 以前知道 90%  
> ↓  
> 只能知道 70%  
> ↓  
> 只能知道 40%  
> ↓  
> 关键设施完全无法核查

风险应该自动上升。

# 八、第三方的“避险行为”往往是极好的领先指标

这是情报系统里非常容易被忽略的一层。

监测：

**使馆撤员、军属撤离、航空公司停飞、船东停航、保险加价、企业撤员、港口改变作业规则、政府旅行警告。**

因为这些机构往往掌握一些公开社会尚未完全掌握的信息。

可以把这种现象叫：

> **Revealed Risk Perception  
> 显性风险偏好/风险认知**

也就是说：

**不要只听别人怎么说，要观察别人拿自己的钱、飞机、船和人员怎么行动。**

# 九、市场数据不是证明战争的证据，但非常适合作为“异常传感器”

你前面提到市场数据是对的，但使用方式必须正确。

油价上涨并不能证明：

> “伊朗准备攻击。”

但是突然出现：

**Brent ↑  
Dubai crude ↑  
柴油裂解价差 ↑  
LNG ↑  
VLCC 运价 ↑  
战争险 ↑  
霍尔木兹船流量 ↓**

而且时间高度同步，

就说明：

> **市场正在共同定价某一种供应中断风险。**

目前油价和航运市场已经明显受到霍尔木兹冲突影响。([Reuters](https://www.reuters.com/business/energy/oil-set-steepest-weekly-gain-since-mid-july-over-intensifying-us-iran-tensions-2026-09-04/?utm_source=chatgpt.com))

所以市场数据更适合叫：

**Risk Sensor**

而不是：

**Fact Evidence。**

# 十、天气数据也应该有，但角色完全不同

天气不是主要威胁情报。

它更像：

> **Context / Constraint**

例如：

卫星照片没看到目标变化，

到底是：

**没有变化**

还是：

**云层遮挡？**

无人机活动减少，

到底是：

**军事行动减少**

还是：

**天气条件恶化？**

因此：

**天气是证据解释器，而不是主要证据。**

这一点在自动化多源分析系统中特别重要。

# 十一、真正关键的是“多源交叉”，而不是“来源越多越好”

我建议你的系统强制区分至少三个证据族：

| 证据族                    | 典型数据                      |
| ---------------------- | ------------------------- |
| **叙事证据 Narrative**     | 政府声明、媒体、Telegram、X、新闻     |
| **物理证据 Physical**      | 卫星、SAR、FIRMS、AIS、ADS-B    |
| **行为证据 Behavioral**    | 船舶绕航、航空停飞、撤员、物流变化         |
| **制度证据 Institutional** | NOTAM、UKMTO、IMO、IAEA、制裁公告 |
| **市场证据 Market**        | 油价、运价、保险、期权               |
| **环境证据 Environmental** | 天气、海况、云量                  |

一个非常重要的规则是：

> **Reuters、CNN、BBC、新华社同时报道，并不等于“四源验证”。**

如果它们全部引用同一个伊朗官员，

实际上仍然是：

**1 个原始来源。**

相反：

> 伊朗声称某油轮被击中  
> 
> + AIS 显示停航  
> + SAR 显示船体异常  
> + UKMTO 接到事故报告  
> + 船东确认受损

才是真正意义上的：

**多源交叉验证。**

# 十二、最终系统不应该输出“情报”，而应该输出“预警状态”

我会把每一个风险事件做成类似这样的状态机：

| 状态          | 含义                     |
| ----------- | ---------------------- |
| 🟢 Normal   | 没有明显异常                 |
| 🟡 Watch    | 出现单一异常信号               |
| 🟠 Warning  | ≥2 个独立证据族出现一致先行指标      |
| 🔴 Critical | 物理准备 + 行为变化 + 官方信号同时出现 |
| ⚫ Event     | 风险事件已经发生               |

例如：

### 「霍尔木兹事实关闭」

可能出现这样的演变：

**伊朗威胁封锁**

↓

🟡

**宣布限制区域**

↓

🟡/🟠

**UKMTO 连续报告袭船**

↓

🟠

**AIS 显示船流量暴跌**

↓

🟠/🔴

**大型油轮集体停止通行 + 保险公司拒保**

↓

🔴

**水雷/武力实际阻断主要航道**

↓

⚫

这时候系统真正告诉决策者的不是：

> “昨天发生了什么。”

而是：

> **“霍尔木兹事实关闭风险已经从 32% 上升到 71%；主要驱动因素为 A/B/C；其中 B 已由两类独立物理证据确认；预计风险窗口为未来数日。”**

这才是我理解的**情报分析预警系统**。

## 结合当前态势，我会首先盯这五条链

截至 9 月 7 日，我认为优先级最高的实际上已经非常明确：

**① 霍尔木兹限制区 → 袭船 → 商船停航 → 事实封锁**

**② 伊朗袭击美军资产 → 美军报复 → 伊朗扩大报复对象 → 下一轮美军更大规模打击**

**③ 导弹/无人机活动增加 → 海湾国家防空启动 → 民航空域关闭 → 误击/外溢风险**

**④ 美国经济和海上封锁压力 → 伊朗财政压力增加 → 伊朗寻求通过能源/航运制造更大全球成本**

**⑤ IAEA 核查缺口扩大 → 核材料状态更加不透明 → 核危机与军事危机相互强化**

其中第 **①、②** 我会放在当前系统的最高优先级，因为最近几天已经同时出现了**军事攻击、航运攻击、流量骤降和新的限制区政策信号**；EASA 也仍将伊朗、伊拉克及波斯湾部分空域维持在冲突风险警告状态。([Reuters](https://www.reuters.com/world/middle-east/iran-says-announce-new-restricted-zone-gulf-coming-days-2026-09-07/?utm_source=chatgpt.com))

这也正好能进一步发展成你前面讨论的**“美伊冲突动态本体”**：

**RiskEvent（风险事件）  
← WarningIndicator（预警指标）  
← Observation（观测）  
← Evidence（证据）  
← Source（来源）**

再加入：

**Actor、Asset、Location、Claim、Action、Capability、Intent、Confidence、Contradiction、Prediction**

系统就会从普通“新闻知识图谱”，真正变成一个**持续运行的情报分析与预警本体**。

如果做这个课题，我认为下一步最值得做的就是直接把上述内容落成一张 **《美伊冲突战略预警指标体系》**：大约 **8 个一级风险事件 → 30-50 个二级预警指标 → 100+ 个具体可采集信号 → 数据源 → 验证规则 → 黄/橙/红触发阈值**。这样 AIS、ADS-B、卫星、新闻、天气、市场、NOTAM、UKMTO、IAEA 等数据就全部有了明确的“为什么采、采来干什么”。

另外，这类态势变化很快，我也可以按这些指标持续监测，只在某条风险链出现明显升级时提醒你。

## 一、先看“不用动态本体”也能怎么做

完全可以做一个传统系统：

新闻采集 → AIS → ADS-B → 卫星 → NOTAM → 市场数据 → 数据库 → 规则引擎 → 风险评分 → 告警。

```text

  霍尔木兹日均通行船数下降 > 60%
AND
  最近24小时发生 >= 2起袭船事件
AND
  伊朗发布新的航行限制
THEN
  霍尔木兹封锁风险 = 高
```

这当然可以运行。

再复杂一点，还可以用：

- Kafka / Flink 做流处理
- PostgreSQL / Elasticsearch 做数据存储

- Drools 做规则
- Python 做评分模型
- Airflow 做工作流
- LLM 做新闻抽取和摘要

技术上全部能实现。

> “没有动态本体就做不到。”

而是：

> **没有动态本体，你必须自己解决本体原本集中解决的那些问题。**

而且随着系统变大，这些问题会越来越明显。

```text
USNavyForceProtectionLevel = Elevated

HormuzClosureRisk.level = Orange
```

这与 Palantir Foundry Ontology 的思路非常接近。

# 四、动态本体还有一个非常重要的作用：维护“时间”

情报里面最容易出错的问题之一，就是：

> 把不同时间发生的事情拼成了同一个事实。

例如：

```text
9月1日
美军舰艇位于 A

9月3日
卫星影像显示伊朗导弹阵地 B 活跃

9月5日
某媒体说伊朗准备攻击美军舰艇
```

如果没有时间语义，很容易直接得到：

```text
导弹阵地 B
threatens
美军舰艇 A
```

但实际上，美军舰艇 9 月 5 日可能早就离开 A。

动态本体应该表达：

```text
Ship
hasPosition
PositionObservation

PositionObservation
validTime
2026-09-01T08:00Z
```

因此系统推理时必须问：

```text
两条证据在时间上是否重叠？
```

这是情报分析里的关键。

所以动态本体实际上维护的是：

> **时空一致性。**

动态本体最大的工程价值之一，就是把这些语义统一起来。

> **Operational Semantic Layer —— 面向真实业务运行的语义操作层。**

例如最高层先定义几个风险事件：

```text
美军基地遭大规模攻击
海湾关键基础设施遭攻击
民航重大安全事故
核危机升级
代理人战线全面扩散
区域能源供应严重中断
```

然后反过来问：

> 哪些现实对象、事件、状态和观测能够导致这些风险发生？

这样本体才天然适合预警。

---

# 二、我建议至少有 12 类核心对象

不宜一开始就设计几百种对象。第一版可以围绕下面这些核心对象。

| 对象                     | 含义                | 示例                 |
| ---------------------- | ----------------- | ------------------ |
| **主体**（Actor）          | 能实施行为的国家、组织、机构等   | 美国、伊朗、CENTCOM、IRGC |
| **资产**（Asset）          | 舰艇、飞机、导弹系统、雷达、油轮等 | 某军舰、油轮、雷达站         |
| **设施**（Facility）       | 基地、机场、港口、核设施等     | 军事基地、炼油厂           |
| **地点/区域**（Location）    | 点、区域、航道、空域        | 霍尔木兹海峡、某FIR        |
| **观测**（Observation）    | 某传感器或来源看到的东西      | AIS航迹点、卫星变化        |
| **指标**（Indicator）      | 从大量观测计算出的统计或特征    | 船流量下降率             |
| **主张**（Claim）          | 某个来源声称发生了什么       | “某油轮遭导弹攻击”         |
| **事件**（Event）          | 经分析认为现实世界实际发生的事情  | 油轮遇袭事件             |
| **证据**（Evidence）       | 支持或反驳某主张/事件的信息    | 卫星、AIS、UKMTO       |
| **状态**（State）          | 对象当前所处的运行状态       | 霍尔木兹=严重受扰          |
| **风险事件**（Risk Event）   | 尚未发生但需要预警的未来事件    | 霍尔木兹事实关闭           |
| **任务/动作**（Task/Action） | 系统或人员需要执行的行为      | 增强监测、复核、告警         |

这里最重要的是：

> **观测 ≠ 事件 ≠ 主张 ≠ 证据。**

这四个一定要分开。

---

# 三、为什么一定要区分“观测、主张、事件”

假设一条新闻说：

> “某伊朗导弹基地被摧毁。”

本体不要立刻生成：

```text
导弹基地.status = Destroyed
```

应该先生成：

```text
主张 C001
类型：设施被摧毁
目标：导弹基地 A
来源：媒体 X
时间：……
```

之后系统获得：

```text
卫星观测 O001
AIS/ADS-B无关
FIRMS热异常 O002
后续卫星变化 O003
官方声明 O004
```

这些变成证据：

```text
O001 → 支持 → C001
O002 → 部分支持 → C001
O003 → 强支持 → C001
O004 → 支持 → C001
```

然后才形成：

```text
事件 E001
导弹基地A遭打击

置信度：高
毁伤程度：严重
是否完全摧毁：尚不能确认
```

这对情报分析非常关键。

---

# 四、关系应该怎么设计

关系不要泛滥。核心关系大约可以分成七组。

## 1. 组织与归属关系

```text
主体
  ├─ 隶属于 → 主体
  ├─ 控制 → 资产
  ├─ 部署 → 资产
  ├─ 使用 → 设施
  └─ 负责 → 区域
```

例如：

```text
IRGC
  控制
某导弹部队
```

---

## 2. 时空关系

```text
资产
  位于 → 地点

事件
  发生于 → 地点

观测
  观测于 → 时间

观测
  覆盖 → 区域
```

所有动态关系都必须有：

```text
有效开始时间
有效结束时间
观测时间
入库时间
```

否则动态本体很容易产生“把昨天和今天拼成一个世界”的错误。

---

# 五、我建议把“时间”做成一等属性

这是军事/情报本体与普通企业本体差别非常大的地方。

比如舰艇位置不能简单写：

```text
USS X
位于
波斯湾
```

应该表达：

```text
位置观测 O10028

目标：
USS X

位置：
P1

观测时间：
2026-09-07 12:03

数据来源：
AIS/卫星/其他

置信度：
0.84
```

当前状态则是动态计算结果：

```text
USS X.currentLocation = 波斯湾

依据：
O10028

更新时间：
12:03
```

这样本体才能保持：

**当前状态 + 历史状态 + 证据来源。**

---

# 六、证据关系是整个情报本体的核心

建议明确建立：

```text
证据
  支持 → 主张

证据
  反驳 → 主张

证据
  支持 → 事件

证据
  反驳 → 事件

证据
  来源于 → 数据源

证据
  派生自 → 原始数据

报道
  引用于 → 原始来源
```

这里还有一个特别重要的关系：

```text
派生自
```

例如：

```text
BBC报道
   派生自
Reuters报道

Reuters报道
   派生自
伊朗官员声明
```

于是三篇新闻不能被算成三个独立来源。

系统可以计算：

```text
报道数量 = 35
独立源数量 = 2
```

这对情报分析极其重要。

---

# 七、风险关系要显式建出来

例如：

```text
袭船事件
   增加风险
霍尔木兹事实封锁

船流下降
   增加风险
霍尔木兹事实封锁

船东暂停通航
   增加风险
霍尔木兹事实封锁

美军护航
   降低风险
霍尔木兹事实封锁
```

不要只写：

```text
risk = 0.78
```

应该同时知道：

> 为什么是 0.78。

也就是：

```text
风险对象
├─ 当前概率
├─ 当前等级
├─ 趋势
├─ 时间窗口
├─ 主要风险驱动
├─ 风险缓释因素
├─ 支持证据
└─ 置信度
```

---

# 八、再说你特别问到的 AIS：数据治理到底在哪里做？

答案很明确：

> **主要在动态本体下面的数据治理和指标特征层做。**

不要让本体直接吞原始 AIS 点。

假设一天有几千万条 AIS：

```text
MMSI
lat
lon
SOG
COG
heading
timestamp
nav_status
...
```

这些原始点应该进入：

```text
AIS原始数据区
```

然后数据治理流水线处理。

---

# 九、AIS 数据治理至少包括这些步骤

```text
原始AIS
   ↓
格式解析
   ↓
字段标准化
   ↓
时间统一
   ↓
坐标合法性检查
   ↓
重复数据消除
   ↓
异常跳点检测
   ↓
船舶身份解析
   ↓
轨迹排序
   ↓
轨迹分段
   ↓
航迹重建
   ↓
空间区域匹配
   ↓
异常特征计算
```

这里很多东西都不适合放在本体运行时实时计算。

例如：

### MMSI / IMO 对齐

同一艘船可能存在：

```text
MMSI
IMO
Call Sign
Ship Name
Vendor ID
```

数据治理层负责解决：

> 这些记录是不是同一个现实世界船舶？

最后得到一个统一对象 ID：

```text
SHIP-00082736
```

本体只认：

```text
船舶 SHIP-00082736
```

下面的数据可以换。

---

# 十、AIS 最后应该给动态本体什么？

不应该主要给：

```text
09:00:01  26.3, 56.4
09:00:04  26.3, 56.4
09:00:09  26.31,56.41
……
```

这些留在时序/轨迹数据存储里。

更适合送入本体的是：

### 当前状态

```text
船舶当前位置
当前航速
当前航向
航行状态
最后观测时间
```

### 聚合指标

例如：

```text
霍尔木兹24小时通航船数
霍尔木兹VLCC通航船数
平均等待时间
掉头船舶数量
异常停航数量
AIS中断比例
平均航速变化
锚地积压数量
```

### 派生事件

例如：

```text
船舶异常掉头事件
异常停航事件
AIS长时间中断事件
异常偏航事件
航道拥堵事件
船流骤降事件
```

这些才真正进入动态本体。

---

# 十一、ADS-B也是完全相同的逻辑

原始 ADS-B 数据：

```text
ICAO24
Callsign
lat
lon
altitude
speed
heading
squawk
timestamp
...
```

先在数据治理层进行：

```text
去重
异常点过滤
时间统一
飞机身份解析
航迹拼接
起降识别
航段识别
机场关联
机型关联
空间区域关联
轨迹特征计算
```

之后才得到本体可以使用的信息。

例如：

```text
某区域军机活动强度
某类支援飞机活动强度
区域空中活动趋势
基地活动变化
航路异常程度
民航绕飞比例
空域使用变化
```

以及：

```text
异常活动事件
活动骤增事件
基地分散事件
区域航路避让事件
```

这里的核心思想仍然是：

> **本体不要替代专业轨迹分析系统。**

---

# 十二、可以把这一层叫“指标与特征层”

这一层在整个系统里非常重要。

它处在：

```text
数据治理

      ↓

指标 / 特征

      ↓

动态本体
```

例如 AIS：

```text
原始AIS轨迹点
       ↓
轨迹分析
       ↓
过去24小时霍尔木兹通航量
       ↓
与30日基线比较
       ↓
-58%
       ↓
形成指标观测
```

进入本体：

```text
指标：
霍尔木兹通航强度

当前值：
42%

基线：
100%

异常程度：
严重

趋势：
下降

时间窗口：
24h
```

这个对象就可以直接参与规则和风险计算。

---

# 十三、因此我甚至建议把“指标”本身做成本体对象

而不是简单做成一个字段。

例如：

```text
指标：霍尔木兹商船通行量

定义：
24小时内穿越指定地理门线的有效商船数量

统计窗口：
24小时

基线：
过去30天同曜日中位数

数据源：
AIS

计算版本：
v1.3

质量等级：
A

更新时间：
2026-09-07 14:00
```

然后才有：

```text
指标观测：

value = 22
baseline = 51
deviation = -56.9%
```

这样做有一个非常大的好处：

**指标定义是可治理的。**

---

# 十四、否则很容易产生一个典型问题

分析员 A 的：

> “霍尔木兹通航量”

是：

```text
进入海峡的所有船
```

分析员 B 的定义是：

```text
完成整个海峡穿越的商船
```

分析员 C 是：

```text
油轮
```

最后大家得到三个数字。

所以指标治理至少应该管理：

```text
指标名称
业务含义
计算公式
时间窗口
空间范围
统计对象
过滤条件
基线定义
单位
数据源
版本
负责人
质量要求
```

这是**数据治理**，但定义完成以后，可以把指标对象暴露给动态本体。

---

# 十五、卫星数据也不要原图直接塞进本体

同样应该经过：

```text
卫星影像
   ↓
几何校正
   ↓
时间/空间统一
   ↓
云量检测
   ↓
变化检测
   ↓
目标检测
   ↓
目标匹配
   ↓
变化解释
```

最后进入本体：

```text
卫星观测

目标：
设施 A

变化类型：
新增毁伤

变化程度：
严重

观测时间：
……

传感器：
SAR

置信度：
0.82
```

原始卫星影像仍然存在对象存储中。

本体只保存：

```text
观测结果
+
原始证据引用
```

---

# 十六、这就带出一个非常重要的设计原则

## 动态本体不是数据仓库。

尤其不能把：

```text
几十亿AIS点
几十亿ADS-B点
PB级卫星数据
全部新闻正文
所有市场tick
```

全物化成一堆本体对象。

否则性能和运维都会非常痛苦。

正确方式是：

```text
                  ┌──────────────┐
                  │ 动态本体     │
                  │              │
                  │ 对象身份     │
                  │ 当前状态     │
                  │ 重要事件     │
                  │ 证据关系     │
                  │ 指标         │
                  │ 风险         │
                  └──────▲───────┘
                         │
                    引用/绑定
                         │
┌───────────────────────────────────────────┐
│ 湖仓 / 时序库 / 空间库 / 对象存储 / 搜索库 │
│                                           │
│ 原始AIS、ADS-B、卫星、新闻、市场……         │
└───────────────────────────────────────────┘
```

一句话：

> **大数据留在数据平台，本体保存“现实世界语义”。**

---

# 十七、数据治理还必须解决一个特别重要的问题：实体解析

这实际上是本体能否成立的基础。

例如 AIS 里：

```text
MMSI = 123456789
ShipName = ABC
```

另外一份 Lloyd's 数据：

```text
IMO = 9876543
ShipName = ABC STAR
```

卫星识别：

```text
目标 Track-781
```

新闻：

> tanker ABC Star

系统必须判断：

```text
这四个是不是同一艘船？
```

数据治理/实体解析系统得到：

```text
Canonical Object ID:
SHIP-00128
```

然后：

```text
MMSI 123456789
IMO 9876543
ABC STAR
Track-781
```

全部：

```text
映射至 → SHIP-00128
```

这就是：

**主数据管理 + 实体解析。**

动态本体以这个统一对象作为基础。

---

# 十八、所以数据治理和本体之间要有一个“语义映射层”

这是工程上非常关键的一层。

可以叫：

**语义映射层（Semantic Mapping Layer）**

负责：

```text
数据表/数据流
      ↓
字段映射
      ↓
对象类型
      ↓
属性
      ↓
关系
      ↓
事件
```

例如：

AIS 表：

```text
mmsi
lat
lon
sog
cog
timestamp
```

映射成：

```text
船舶对象
   ObjectID = resolve(mmsi)

位置观测
   target = ObjectID
   lat
   lon
   speed = sog
   course = cog
   observed_at = timestamp
```

这就是数据与动态本体真正的接口。

---

# 十九、我建议定义统一的“观测数据契约”

所有数据源最终进入本体以前，都尽量转换成统一结构。

例如：

```text
观测ID
对象ID
观测类型
观测时间
有效时间
空间位置
数据来源
观测值
质量评分
置信度
原始数据引用
处理算法
算法版本
```

这样：

AIS、ADS-B、卫星、市场、天气

虽然完全不同，但最终可以变成统一的：

```text
Observation
```

本体就不用知道底层用了 Kafka、Parquet 还是 PostgreSQL。

---

# 二十、再说“规则”：我建议至少分成六类

这里也很重要。

### 第一类：实体与融合规则

例如：

```text
如果：
MMSI一致
AND
IMO一致

则：
判定为同一船舶
```

严格来说，这类更多运行在数据治理/实体解析层。

---

### 第二类：事实核验规则

例如：

```text
若：
官方主张：油轮被击中

AND
UKMTO独立报告支持

AND
AIS出现异常停航

AND
卫星影像出现对应变化

则：
油轮遇袭事件置信度 → 高
```

这属于动态本体层。

---

### 第三类：状态转换规则

例如霍尔木兹：

```text
正常
↓
紧张
↓
受扰
↓
严重受扰
↓
事实关闭
```

规则：

```text
如果：
24小时通行量下降 > 50%

AND
7天袭船事件 >= 3

则：
受扰 → 严重受扰
```

---

### 第四类：风险推理规则

例如：

```text
若：

霍尔木兹状态 = 严重受扰
AND
大型油轮停航比例显著增加
AND
战争险显著增加

则：

霍尔木兹事实封锁风险 ↑
```

---

### 第五类：矛盾检测规则

例如：

```text
新闻声称：
港口完全关闭

BUT

AIS显示：
大量商船持续正常进出

则：

主张置信度下降
+
生成“证据冲突”
```

这一类非常适合情报分析。

---

### 第六类：预警触发规则

例如：

```text
风险等级
黄色 → 橙色
```

触发：

```text
分析员复核
+
增加采集频率
+
生成风险简报
```

---

# 二十一、“动作”应该比告警丰富得多

很多系统所谓动作只有：

> 发短信。

实际上动态本体最有价值的地方之一，就是动作。

我建议至少有以下动作类型。

| 动作         | 作用              |
| ---------- | --------------- |
| **补充采集**   | 要求系统查找更多相关数据    |
| **增强监测**   | 提高某区域、对象、指标监测频率 |
| **人工复核**   | 创建分析员任务         |
| **事实核验**   | 针对一个争议主张发起验证    |
| **风险重算**   | 立即重新计算某风险       |
| **生成情报产品** | 自动形成态势简报        |
| **发送预警**   | 通知值班员、决策人员      |
| **升级事件**   | 黄→橙→红           |
| **添加重点对象** | 纳入观察名单          |
| **启动专题分析** | 建立临时专题          |
| **请求新数据源** | 获取额外卫星、海事、航空等数据 |

动作还可以更新本体。

例如：

```text
创建分析任务
    ↓
分析员完成
    ↓
形成新评估
    ↓
本体状态更新
```

因此是闭环，不是单向流水线。

---

# 二十二、现在可以把整个美伊预警闭环真正串起来

假设监测：

> **霍尔木兹事实封锁风险**

第一步，持续感知：

```text
AIS
UKMTO
卫星
新闻
船东公告
保险
油价
天气
```

↓

第二步，数据治理：


# 二十三、还有一个非常关键的边界

我建议记住这一条：

> **数据治理回答“这条数据能不能用”；**
> 
> **动态本体回答“这条数据对于现实世界意味着什么”。**

例如 AIS：

数据治理层发现：



这是数据治理。

动态本体进一步判断：

```text

```

这是本体语义。

又比如：

```text

```

计算这个 58%：

**数据工程。**

解释它：


**动态本体。**

再进一步：


是：

**风险推理。**

再进一步：

```text

```

是：

**动作闭环。**

这几个层次千万不要混在一起。

```text
对象 ─位于→ 区域
事件 ─发生于→ 区域
观测 ─针对→ 对象
观测 ─发生于→ 时间
资产 ─进入→ 区域
资产 ─离开→ 区域
航迹 ─穿越→ 区域
```

但是这里有一个重要原则：

```text
“资产位于区域”
```

最好不要只有一个永久边。

应该带：

```text
开始时间
结束时间
依据观测
置信度
```

---

# 二十、第三组：行为与事件关系

解决：

> 谁做了什么？

例如：

```text
主体 ─实施→ 事件
主体 ─参与→ 事件
资产 ─参与→ 事件
事件 ─攻击→ 资产
事件 ─影响→ 设施
事件 ─导致→ 状态变化
事件 ─发生于→ 区域
```

例如：

```text
导弹攻击事件E23
   攻击
军事基地F7
```

而不是简单：

```text
伊朗 → 美国基地
```

中间必须有：

> 事件对象。

# 二十一、第四组：观测与证据关系

解决：

> 我们为什么相信这件事？

```text
观测 ─观测到→ 对象
观测 ─来源于→ 数据源
观测 ─派生自→ 原始记录

证据 ─基于→ 观测
证据 ─支持→ 主张
证据 ─反驳→ 主张
证据 ─支持→ 事件
证据 ─反驳→ 事件
```

例如：

```text
AIS异常停航观测
       ↓
     形成
       ↓
证据E11
       ↓
     支持
       ↓
油轮遭攻击事件
```

---

# 二十二、第五组：主张与来源关系

这是 OSINT 系统特别重要的一组。

解决：

> 谁最先说的？谁只是转述？

```text
主张 ─由…提出→ 主体
主张 ─发布于→ 数据源
主张 ─涉及→ 对象
主张 ─声称发生→ 事件类型

报道 ─引用→ 主张
报道 ─转载自→ 报道
主张 ─派生自→ 主张
```

例如：

```text
伊朗官员
    ↓提出
Claim001
    ↓被引用
Reuters
    ↓被引用
BBC
    ↓转载
若干社交媒体
```

系统最终知道：

```text
报道数量：37

独立原始来源：
1
```

这个关系组非常关键。

# 二十三、第六组：因果、影响与风险关系

解决：

> 某件事情为什么会提高某种风险？

例如：

```text
事件 ─增加风险→ 风险事件
事件 ─降低风险→ 风险事件

指标 ─支持→ 风险事件
指标 ─反向支持→ 风险事件

风险事件 ─可能导致→ 风险事件
风险事件 ─影响→ 对象
风险事件 ─影响→ 区域
```

例如：

```text
连续袭船事件
   增加风险
霍尔木兹事实关闭
```

```text
美国海军护航能力增强
   降低风险
霍尔木兹事实关闭
```

以及风险传播：

```text
霍尔木兹事实关闭
      ↓可能导致
海湾能源供应严重中断
      ↓可能导致
国际油价剧烈上涨
```

# 二十四、第七组：任务、规则和动作关系

解决：

> 判断发生变化之后，系统怎么办？

```text
风险事件 ─触发→ 规则
规则 ─触发→ 动作
动作 ─创建→ 任务
任务 ─针对→ 对象
任务 ─产生→ 评估
评估 ─更新→ 风险事件
动作 ─更新→ 对象状态
```

形成真正闭环：

```text
风险上升
   ↓
规则命中
   ↓
创建分析任务
   ↓
分析员核验
   ↓
形成评估
   ↓
风险重新计算
```

这就是上一轮欠缺的五组。

# 二十五、再往下：美伊冲突预警到底需要哪些状态机

第一版至少应该做 5 个。

## 状态机一：美伊整体冲突态势

```text
低烈度对抗
      ↓
有限军事冲突
      ↓
周期性直接交火
      ↓
持续高强度军事冲突
      ↓
区域战争
```

状态判断依据：

```text
打击频率
攻击目标类型
参与兵力规模
持续时间
攻击区域数量
第三方卷入程度
```

---

# 二十六、状态机二：霍尔木兹海峡

```text
正常
 ↓
紧张
 ↓
局部受扰
 ↓
严重受扰
 ↓
事实关闭
 ↓
恢复
```

典型条件：

### 紧张

```text
军事威胁增加
OR
航行限制增加
```

### 局部受扰

```text
袭船增加
OR
通行量明显下降
```

### 严重受扰

例如：

```text
24小时通行量低于30日基线50%

AND

存在持续安全事件
```

### 事实关闭

不能只根据：

> 伊朗宣布“关闭”。

应该看行为事实：

```text
大型商船通行量接近停止

+
大型船东停止通行

+
保险/航运市场确认极端风险

+
物理威胁持续存在
```

# 二十七、状态机三：军事基地

例如美国某海湾基地：

```text
正常
 ↓
警戒
 ↓
高度戒备
 ↓
可能遭攻击
 ↓
遭攻击
 ↓
部分失能
 ↓
恢复
```

先行指标可能包括：

```text
军机分散
防空活动
人员撤离
NOTAM变化
基地航班活动异常
相关官方警告
```

# 二十八、状态机四：舰艇

```text
正常航行
 ↓
提高戒备
 ↓
战术机动
 ↓
交战
 ↓
受损
 ↓
失去行动能力
```

ADS-B/AIS 本身不一定能完全看到军舰，但公开海事、卫星、官方声明等可以共同补充。

# 二十九、状态机五：风险事件

所有风险统一：

```text
正常
 ↓
关注
 ↓
黄色预警
 ↓
橙色预警
 ↓
红色预警
 ↓
已发生
 ↓
解除/恢复
```

建议：

> 风险状态与概率分数分开。

例如：

```text
概率 = 0.68

状态 = 橙色
```

因为最终状态可以综合：

```text
概率
影响程度
时间紧迫性
判断置信度
```

而不应该机械：

```text
>60% = 橙色
```

# 三十、具体规则应该怎么设计

这里不要做“一套大规则”。

建议分成 7 类规则。

---

## 规则一：数据质量规则

这部分主要运行在数据治理层。

例如 AIS：

```text
若：

5分钟内位置跳变 > 300海里

则：

该AIS观测质量 = 极低
不允许更新船舶当前位置
```

ADS-B 同理。

---

# 三十一、规则二：对象融合规则

例如：

```text
若：

MMSI一致
AND IMO一致

则：

映射为同一船舶对象
```

更复杂的可以使用：

```text
名称
尺寸
船型
轨迹
历史映射
```

综合匹配。

---

# 三十二、规则三：事件识别规则

例如：

### 船舶异常掉头事件

```text
若：

船舶进入霍尔木兹接近区

AND

航向在短时间内变化 > X°

AND

随后驶离海峡

则：

创建：
异常掉头事件
```

注意：

> X 不能写死在本体代码中。

应该是配置化规则参数。

---

# 三十三、规则四：事实核验规则

例如：

```text
主张：
油轮A遭攻击
```

若：

```text
UKMTO报告支持

+
AIS出现异常停止

+
卫星/SAR出现对应变化
```

则：

```text
事件：
油轮A遭攻击

事实置信度：
高
```

如果：

```text
仅存在10篇新闻

但均引用同一个匿名消息源
```

则：

```text
独立证据数 = 1
```

置信度不能机械提升。

---

# 三十四、规则五：状态转换规则

例如霍尔木兹：

```text
如果：

24小时商船通行量偏离基线 < -50%

AND

72小时内有效袭船事件 >= 2

AND

大型航运企业停航比例明显增加

则：

状态：
局部受扰 → 严重受扰
```

---

# 三十五、规则六：风险推理规则

例如 R4：

> 霍尔木兹事实关闭。

可以把风险驱动分成：

### 威胁能力

```text
袭船能力
水雷能力
岸基导弹活动
无人机活动
```

### 行动意图

```text
政治声明
IRGC声明
限制区域
军事部署
```

### 实际行为

```text
袭船
扣船
干扰
限制航行
```

### 外部响应

```text
船舶掉头
船东停航
保险上涨
海军护航
```

所以不是简单：

```text
risk = 新闻情绪
```

而是：

```text
风险 =
能力
×
意图
×
行为
×
环境脆弱性
×
外部响应
```

实际实现可以是规则、统计模型、贝叶斯网络或机器学习。

动态本体负责组织变量及语义。

# 三十六、规则七：预警触发规则

例如：

```text
若：

R4风险等级
黄色 → 橙色

则执行：

A01 创建高级别分析任务
A02 AIS刷新频率提升
A03 检查最新UKMTO信息
A04 检查船东停航公告
A05 检查保险数据
A06 自动生成风险简报
```

# 三十七、动作到底应该设计哪些

第一版我建议 12 种。

### A01 创建分析任务

```text

“核验霍尔木兹通航异常”
```

### A02 请求补充采集

例如：

```text
请求查询：

```

---

### A03 增强监测

例如：

```text
AIS指标刷新周期
30分钟 → 5分钟
```

---

### A04 扩大监测对象

例如：

```text
增加：
所有VLCC
所有LNG船
重点美军基地
```

---

### A05 重新计算风险

```text
立即重算 R4
```

---

### A06 触发事实核验

针对：

```text
“伊朗已经封锁霍尔木兹”
```

### A07 生成预警简报

输出：

```text

什么尚未确认
风险为什么上升
未来时间窗口
需要继续观察什么
```

---

### A08 通知

根据级别：

```text
黄色 → 值班分析员
橙色 → 主管
红色 → 决策层
```

---

### A09 更新重点观察名单

例如：

```text
某导弹部队
某军事基地
某海域
```

进入高优先级监控。

---

### A10 调整数据采集优先级

例如：

```text
普通区域卫星查询优先级 ↓

霍尔木兹 ↓
最高
```

---

### A11 请求人工裁决

当：

```text
高价值结论
+
证据高度矛盾
```

不能自动决定。

---

### A12 关闭/降级预警

例如：

```text
连续72小时指标恢复
+
安全事件显著下降
```

允许：

```text
红 → 橙 → 黄
```

而不是只会升级不会降级。

# 四十二、ADS-B则应该治理出什么

针对美伊冲突，不应该把重点放在：

> 某架飞机的每个点。

而应该重点形成：

### 轨迹事件

```text
起飞
降落
进入区域
离开区域
异常盘旋
异常返航
航路偏移
```

### 区域活动指标

例如：

```text
区域航空活动总量
民航活动量
军用公开航迹活动量
某类机型活动强度
机场起降量变化
民航绕飞比例
空域关闭范围
```

需要强调：

> 公开 ADS-B 数据对军事航空活动天然不完整，因此“未看到”绝不能直接解释成“没有活动”。

这应该直接进入数据质量和证据可信度模型。

# 四十三、那么治理后的数据怎么映射进动态本体

可以建立统一的：

## 语义接入层

例如 AIS：


映射：

```text
→ 指标定义：

```

```text

```

```text

```

然后：

```text

   关联
霍尔木兹海峡

指标观测
   支持
航运严重受扰状态

   增加风险

```

这就是数据和本体之间最重要的桥梁。

# 四十五、最重要的一点：哪些事情不要放进动态本体

第一版尤其要克制。

以下工作不要让动态本体做：

```text
AIS轨迹拼接
ADS-B轨迹清洗
卫星影像预处理
OCR
新闻HTML清洗
文本去重
时间格式标准化
坐标投影转换
海量历史指标计算
模型训练
```

这些属于：

```text
数据平台
数据治理
专业算法服务
```

动态本体处理：

```text
这是什么对象？

发生了什么？

证据支持什么？

当前状态是什么？

风险正在怎么变化？

接下来应该做什么？
```

# 四十七、如果把 v1 压缩到真正可以开始开发的最小集合

其实第一阶段甚至不用 14 个对象全部实现。

我会优先做这 **9 个核心对象**：

```text
主体
资产
区域
观测
指标
主张
事件
证据
风险事件
```

配套：

```text
状态
规则
动作
```

先只做三个风险：

```text
R1 美伊直接军事升级
R2 美军资产遭大规模攻击
R4 霍尔木兹事实关闭
```

再接四类数据：

```text
新闻/官方声明
AIS
ADS-B
UKMTO/NOTAM
```

卫星作为第二阶段加入。

这样规模会非常可控，而且已经足以验证一个核心命题：

> **动态本体能否把多源数据从“很多信号”，转换成“一个风险对象正在发生什么变化，以及为什么”。**

这比一开始构建一个“中东战争超级知识图谱”靠谱得多。

下一步如果继续往实现级推进，我建议就从 **R4“霍尔木兹事实关闭”** 单独挑出来，把它做成一个完整样板：逐项定义它所依赖的 **对象字段、AIS指标口径、事件识别规则、证据权重、状态转换条件、风险计算和动作触发**。这个样板做通以后，R1、R2、R3 基本就可以沿同一框架扩展。
