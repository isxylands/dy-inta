## 1. 结论先行

场景 2 和场景 3 应该作为第二条主线合并演示，定位为：

> 区域安全事件信息降噪与关键基础设施韧性监测

场景 2 负责回答“外部信息洪水里哪些消息可信、哪些只是传闻、哪些需要继续核验”；场景 3 负责回答“如果某个关键设施被声称受影响，设施是否真的受损、服务是否中断、恢复是否可信、后续应该监测什么”。

这条主线比单纯复盘冲突更容易打动海湾客户，原因是：

1. **它服务防护而非进攻**：重点是保护港口、机场、电力、海水淡化、能源、数据中心和航运服务连续性。
2. **它解决真实痛点**：危机期间最大问题不是“有没有消息”，而是消息太多、真假难辨、传播太快，决策者需要降噪、验证和持续监测。
3. **它能体现 L1/L2/L3 闭环**：新闻/社媒线索进入一级预警，火点/影像/官方通告做二级验证，最终形成三级设施韧性报告和持续监测任务。
4. **它比场景 1/4 更贴近“守卫和平”叙事**：输出公共安全、民防、港口调度、备用能力、服务恢复和证据不足提示，而不是军事归因或行动建议。

现有样例数据可以起步，但还不够直接 demo：

- `sample-news-dataVISA0260613.xlsx`、`news行为分析表V20260615.xlsx`、`知识库20260602.xlsx` 的信息域规则非常适合场景 2，但需要从“军事预警/战术判断”改写为“主张抽取、传闻降级、民用影响评估”。
- `卫星行为分析表V20260615.xlsx` 和 4 张 T0/T1/T2/T3 图片适合演示多时相影像变化检测，但图片内容是机场/基地停机坪活动变化，不是港口、能源、电力、海水淡化或数据中心的损伤恢复证据。
- `地理知识库_字段表_完整版.xlsx` 对 AOI 和设施库有启发，但当前偏海域、港口、机场、军事敏感区，缺关键民用基础设施组件级边界。
- `多源融合场景行为分析表V20260615.xlsx` 的“多源验证提升置信度”框架可以复用，但具体场景名称和输出等级需要去进攻化、去打击化。

第一版 demo 不应追求全自动。推荐做一个固定事件包：

> 某海湾关键设施附近出现“爆炸/无人机/火灾/服务中断”多源传闻，系统自动聚类主张，区分官方确认、媒体转述、社媒复用、旧视频风险；随后用火点、卫星多时相、机场/港口/网络/航运运营指标验证，输出“部分验证/证据不足/已反驳/需持续监测”的设施韧性报告。

## 2. 场景 2/3 应如何合并

### 2.1 不是两个烟囱，而是一条链

场景 2 和场景 3 的关系不是并列页面，而是同一条情报生产链的前后段：

```text
信息域主张
  → 事件聚类与传闻降噪
  → 影响设施候选
  → 火点/影像/官方通告/运营指标验证
  → 损伤与服务影响判断
  → 恢复进度与持续监测任务
  → 三级设施韧性报告
```

如果拆成两个 demo，会造成：

- 场景 2 只剩新闻热词和舆情图，不能说明业务价值。
- 场景 3 缺少事件触发来源，看起来像普通遥感变化检测。
- 两边都会重复设施、AOI、证据、置信度和报告对象。

合并后，场景 2 负责“把噪声压下去”，场景 3 负责“把影响讲清楚”。

### 2.2 推荐命名

推荐客户侧名称：

> 关键基础设施韧性监测与危机信息降噪

推荐工程侧名称：

> Scenario B: Critical Infrastructure Impact Assessment

推荐能力包拆分：

| 能力包 | 对应原场景 | 目标 |
| --- | --- | --- |
| 事件信息降噪 | 场景 2 | 将新闻、社媒、官方声明拆成可追溯主张，聚类、去重、识别矛盾和旧视频风险 |
| 民用影响评估 | 场景 2/3 | 判断机场、港口、电力、海水淡化、能源、数据中心等是否受影响 |
| 设施韧性监测 | 场景 3 | 用多时相影像、火点、运营指标和官方通告持续跟踪损伤与恢复 |
| 证据链报告 | 场景 2/3 | 输出结论、置信度、剩余不确定性、非进攻性建议和后续监测计划 |

## 3. Demo 应打动用户的核心设计

### 3.1 客户真正关心的问题

面向阿联酋/海湾客户，demo 不应围绕“谁打了谁”展开，而应围绕这些问题：

1. 哪些传闻值得关注，哪些只是重复转发或旧视频？
2. 某个机场、港口、能源设施、海水淡化厂、电站、数据中心是否真的受影响？
3. 影响是安全风险、运营中断、供应链压力、公共服务影响，还是只是不确定线索？
4. 官方称“运行正常”或“已恢复”，外部证据是否支持？
5. 如果证据不足，下一步应该调什么数据、等什么影像、监测哪些指标？
6. 如何向高层输出一页清楚、可追溯、不过度断言的风险简报？

### 3.2 推荐演示脚本

第一版演示建议固定 7 步：

1. **L1 信息洪水进入**：导入 20-50 条新闻/社媒/官方声明样例，包含爆炸、无人机、火灾、设施中断、否认、旧视频转发、外交表态等混合内容。
2. **主张抽取**：系统把每条文本拆成 `SecurityIncidentClaim`，保留来源、时间、地点、主张类型、被声称目标、原文链接和提取置信度。
3. **聚类与降噪**：系统把同一地点、同一时间窗、同类表述聚成事件线索，识别重复媒体、矛盾说法、低可信来源、旧视频风险。
4. **影响设施候选**：系统根据 AOI 和设施库找出可能受影响的港口、机场、电力、海水淡化、能源、数据中心或通信服务。
5. **L2 多源验证**：火点/热异常、T0/T1/T2/Tn 影像、官方通告、机场/港口/网络/航运指标分别给出支持、反驳或待确认。
6. **L3 设施韧性报告**：输出关键判断、证据矩阵、置信度变化、民用影响、剩余不确定性和后续监测任务。
7. **持续监测**：把事件转成 `MonitoringTask`，设定下一次火点、影像、官方通告和运营指标检查。

### 3.3 演示页面建议

| 页面 | 目标 | 关键组件 |
| --- | --- | --- |
| 危机信息流 | 展示信息洪水和降噪价值 | 新闻/社媒/通告列表、主张抽取、来源可靠性、重复/矛盾标记 |
| 事件聚类地图 | 展示线索如何从文本落到地理对象 | 事件簇、影响 AOI、可能受影响设施、粗粒度热区 |
| 验证矩阵 | 展示系统不把单源主张当事实 | 新闻、官方、火点、影像、运营指标、网络指标的支持/反驳/待确认 |
| 设施韧性面板 | 展示“用户该怎么保护资产” | 设施组件、运行状态、损伤评估、恢复证据、服务影响、监测任务 |
| 高层报告 | 展示可交付成果 | 结论先行、证据链、置信度、不确定性、非进攻建议 |

### 3.4 推荐第一版事件包

不建议第一版做真实复杂冲突全量复盘。建议固定一个可控事件包：

| 要素 | 建议 |
| --- | --- |
| 地区 | 阿联酋/阿曼/海湾关键基础设施走廊，粗粒度 AOI |
| 设施类型 | 港口、机场、电力/海水淡化综合体、能源设施、数据中心任选 1 个主设施 + 2 个邻近备选设施 |
| 事件主张 | “附近发生爆炸/火灾/无人机传闻/服务中断/官方否认”混合 |
| 二级证据 | NASA FIRMS 火点、T0/T1/T2/Tn 光学或 SAR 影像、官方公告、运营指标 |
| 输出 | “部分验证”“已反驳”“证据不足”“持续监测”四类状态都要出现 |

关键设计：demo 里必须至少有一条主张被降级或反驳，否则系统看起来只会把所有消息升格成警报。

## 4. 现有样例数据逐项判断

### 4.1 `sample-news-dataVISA0260613.xlsx`

结构：

| 字段 | 用途 |
| --- | --- |
| `标题` | 主张抽取、事件聚类 |
| `来源` | 来源可靠性和媒体类型 |
| `时间` | 事件时间线 |
| `地点`、`纬度`、`经度` | 地理落点和 AOI 匹配 |
| `摘要` | 主张内容和实体抽取 |
| `风险`、`置信度` | 样例评分，可作为初始值但不能直接采信 |
| `标签` | 分类种子 |
| `实体名称` | 组织、国家、人物、设施实体候选 |
| `原始内容` | 来源链接 |

可用价值：

- 能做 L1 新闻线索列表。
- 能演示同日同地多条报道聚类，例如 2026-05-28、2026-06-10、霍尔木兹海峡、阿巴斯港等。
- 能演示矛盾与不确定性，例如“达成协议/否认协议”“击落/否认”“冲突升级/谈判继续”。
- 能提取能源、封锁、无人机、爆炸、官方声明、外交谈判等主题。

主要问题：

- 多条内容包含高风险断言或明显演示化叙事，不能当事实。
- `置信度` 字段格式不统一，例如 `高88`、`高9`、`高8`，需要清洗。
- 缺 `claim_status`、`source_type`、`collected_at`、`language`、`original_text_hash`、`media_hash`、`repost_of` 等降噪字段。
- 缺官方声明、社媒原帖、视频/图片反查结果。

建议处理：

- 保留为 `SecurityIncidentClaim` 样例输入。
- 所有行默认状态应是 `single_source_claim` 或 `rumor`，不得默认 `verified`。
- 增加人工标注列：`claim_type`、`target_facility_candidate`、`claim_status`、`verification_need`、`safety_boundary_note`。

### 4.3 `知识库20260602.xlsx`

可复用内容：

- `IB001` 至 `IB010` 信息行为，如关键词爆发、时空聚焦、信源突变、传播爆发、内容高度一致、官方警告声明。
- `场景规则库` 中“虚实联动异常”“信号遮蔽伪造”“冲突升级态势”等可转成跨域验证规则。

- 仅复用信息行为、地理对象、规则表达格式和风险等级思想。
- 把所有高风险动作改写为 `create_lead_card`、`request_imagery_check`、`assign_review`、`generate_fusion_report`、`create_monitoring_task`、`publish_safety_recommendation`。
- 不复用“打击”“战前”“意图推断”作为 demo 结论。

### 4.5 `卫星4张图片`

本轮目视检查结论：

| 文件 | 内容判断 | 可用性 |
| --- | --- | --- |
| `T0-YLWX01.png` | 机场/基地停机坪，停放目标较少 | 可作为 T0 基线 |
| `T1-YLWX01(1).png` | 停机坪新增多个飞机目标 | 可作为 T1 活动增加 |
| `T2-YLWX01.png` | 目标数量继续增加，位置变化明显 | 可作为 T2 活动变化 |
| `T3-YLWX0.png` | 新增大型飞机和更多停机坪目标 | 可作为 T3 活动高峰 |

适合展示：

- 多时相影像对比。
- 目标新增、目标移动、目标数量变化。
- 机场/停机坪活动强度变化。
- `ImageryAsset`、`DetectionObject`、`changed_from`、`VerificationMatrix` 的样例链路。

不适合直接展示：

- 关键基础设施损伤。
- 恢复进度。
- 港口、能源、电力、海水淡化或数据中心韧性。
- 真实事件验证。

建议：保留为“多时相变化检测能力样例”，但第一版客户 demo 还需要补一组真正的关键基础设施 T0/T1/T2/Tn 影像。

### 4.6 `地理知识库_字段表_完整版.xlsx`

可复用内容：

- 地理 AOI 的字段设计。
- 港口、海峡、机场、气象、海况、国家边界、岛屿等字段。
- 数据源清单，如 Marine Regions、PortWatch、Natural Earth、World Port Index、NOAA 海洋预报。

需要补强：

- 关键设施表不应只有点位，需要 polygon 和 component geometry。
- 缺海水淡化厂、电力/海水综合体、变电站、油库、炼厂、LNG、数据中心、通信枢纽、港口泊位、机场跑道/航站楼/油库等组件级对象。
- “敏感区/军事禁区”应在客户 demo 中弱化，重点转为“民用基础设施保护区、服务范围、影响范围、备用服务范围”。

### 4.7 `多源融合场景行为分析表V20260615.xlsx`

可复用内容：

- 多源验证提升置信度的思路。
- “新闻 + 卫星 + AIS/ADS-B”的组合验证模式。
- 最小验证要求和决策矩阵。

主要问题：

- 现有 15 个场景几乎都偏军事部署、封锁、空袭前兆、防空激活等，不适合直接用于场景 2/3 的防护叙事。
- “单源 85% → 多源 95%”这类提升公式过硬，缺少证据权重、矛盾证据和数据新鲜度。

建议改写成以下场景：

| 新场景 ID | 场景名称 | 数据源组合 | 输出 |
| --- | --- | --- | --- |
| `CIR001` | 设施爆炸/火灾主张验证 | 新闻 + FIRMS + 影像 + 官方通告 | 部分验证/反驳/待确认 |
| `CIR002` | 机场运行影响评估 | 新闻 + ADS-B/航班 + 影像 + NOTAM/官网 | 延误、取消、跑道可用性、恢复状态 |
| `CIR003` | 港口运营影响评估 | 新闻 + AIS + 港口公告 + 影像 | 泊位活动、排队、服务中断 |
| `CIR004` | 电力/海水淡化服务风险 | 新闻 + 夜光/热异常 + 官方公告 + 服务指标 | 服务连续性和备用能力 |
| `CIR005` | 数据中心/网络服务影响 | 新闻 + IODA/RIPE/Cloudflare + 设施库 + 官方公告 | 网络中断、影响范围、恢复趋势 |
| `CIR006` | 旧视频/错误地理定位降级 | 社媒 + 媒体哈希 + 地理定位 + 反向搜索 | 降级或反驳 |

### 4.8 `system.event_trajectory1_20260613.xlsx` 与 `事件数据AISV2_0260613.xlsx`

这两个样例主要服务场景 1/4。对场景 2/3 的价值有限，但可作为辅助：

- ADS-B 样例可以辅助机场运行状态或空域绕飞分析，但字段和样例偏军事航空目标，不适合直接做民用防护主线。
- AIS 样例可以辅助港口运营和航运影响，但当前样例偏航母/军事舰艇，需换成商船、油轮、集装箱船、LNG 船等民用航运数据。

## 7. 规则改写建议

### 7.1 原子规则

| 原始规则类型 | 保留 | 改写方向 |
| --- | --- | --- |
| 关键词命中 | 保留 | 从“军事行为”改成“主张类型” |
| 多源一致 | 保留 | 要同时支持“多源一致”和“多源互相引用但同源” |
| 信息矛盾 | 保留 | 输出 `conflicting_claims`，不直接说信息战 |
| 官方沉默 | 谨慎保留 | 只能表示 `official_not_confirmed`，不能解释为隐瞒 |
| 火点匹配 | 新增 | 爆炸/火灾主张与 FIRMS 同窗同区匹配 |
| 影像变化 | 新增/改写 | 设施组件变化、活动变化、损伤候选、恢复候选 |
| 运营变化 | 新增 | 航班、港口、网络、船舶活动低于基线 |

### 7.2 置信度规则

不要使用简单的“单源 85% → 多源 95%”。建议第一版使用可解释加减分：

| 证据 | 作用 |
| --- | --- |
| 权威官方通告支持 | 大幅提高置信度，但仍保留通告范围 |
| 多家独立媒体一致 | 中幅提高，需确认不是同一源转载 |
| FIRMS 同窗同区火点 | 支持火灾/爆炸，但需排除工业常态火炬 |
| T0/T1 影像显示新增损伤 | 支持设施影响 |
| 运营指标下降 | 支持服务影响 |
| 官方否认但无其他证据 | 降低但不直接反驳 |
| 影像无变化 | 对“设施损伤”形成反证，但需说明影像时间和分辨率 |
| 旧视频/错地理定位 | 强反证，降级为误传或无关 |
| 云量高/分辨率低 | 标记证据不可用，不提高也不降低 |

### 7.3 状态机

推荐状态：

```text
rumor
  → single_source_claim
  → clustered_claim
  → partially_verified
  → verified
  → monitoring
```

旁路状态：

```text
refuted
inconclusive
stale
duplicate
out_of_scope
needs_analyst_review
```

### 7.4 安全边界规则

所有报告建议必须限制在：

- 继续监测。
- 调取下一期影像。
- 等待官方通告。
- 通知民防/港口/机场/能源运营方。
- 调整公共安全提示。
- 评估备用服务和恢复资源。
- 标记证据不足，避免扩散未经验证消息。

禁止输出：

- 打击目标选择。
- 武器发射点推断。
- 精确军事部署坐标。
- 进攻性处置建议。
- 未经验证的归因断言。

## 11. 当前最重要的取舍

1. **先做可信闭环，不做“大而全”**：第一版只要一个事件包打透 L1/L2/L3，比铺 10 个地图图层更有说服力。
2. **让系统会反驳和降级**：只会升级预警的系统不可信。demo 必须展示“旧视频/无火点/影像无变化/官方未确认”如何降低置信度。
3. **场景 3 要有真实设施数据**：没有设施组件、运营指标和 T0/T1/T2/Tn，韧性监测就会退化成普通遥感看图。
4. **现有规则要换话术和动作**：保留结构，不保留进攻性结论。
5. **不要过度自动化承诺**：第一版可以人工标注影像检测和主张状态，但要把数据结构设计成未来可自动化。
