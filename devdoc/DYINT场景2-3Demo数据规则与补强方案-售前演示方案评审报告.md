## 1. Review 结论

Gate：**需结构性补强后复审**。

核心判断：这份材料作为内部 Demo 数据、规则和动态本体补强底稿已经有价值；作为直接面向客户的售前演示方案，还不够。它有清晰的防御型方向、对象和数据框架，但客户版故事没有完全立住，文档也混入了作者写作思路、工程拆解和数据待办。售前现场需要的是“我现在承受什么压力、系统让我少犯什么错、我能看到什么画面、我下一步能做什么”，而不是先读懂一套内部建设说明。

建议把客户版一句话业务故事改成：

> 当海峡传来袭击、封锁或设施受损传闻时，客户最怕的不是少看一条数据，而是在真假未明时错过准备窗口；这个 Demo 要让值班主管看到，系统如何把新闻、船舶/航空轨迹、海事通告、卫星影像和火点证据合成一张可追溯判断单，告诉值班团队哪些船、航道和能源设施需要立刻复核、加强监测和提前准备。

这句话比原文更适合作为客户主线，因为它先说客户真实焦虑，再说系统动作，最后落到业务结果：**少错判、早准备、可追溯**。

## 3. 本次风险模型

被保护资产：

- 客户信任：客户是否相信系统能减少误判，而不是觉得材料在包装概念。
- 售前推进：客户是否愿意继续给数据、给场景、给试点机会。
- 合规边界：材料是否避免被理解为进攻性军事研判或生产控制承诺。
- 工程可交接性：数据、规则、本体和演示资产是否能被后续团队执行。

关键变更动作：

- 把内部数据规则方案改造成客户能听懂的 Demo story。
- 把动态本体、规则和数据需求转成可见画面、证据链和业务动作。
- 把高敏军事叙事降级为航行安全、设施保护、持续监测和复核报告。

主要不确定性：

- 5 月 25-28 日、6 月 8-11 日窗口是否真的有足够可展示证据。
- 场景 3 是否能找到真实能源/港口设施的 T0/T1/T2/Tn、火点和运营证据。
- 海贝 AIS/ADS-B 身份字段、去重、AOI 和可展示授权是否能支撑客户演示。
- 当前系统已有能力、mock 能力和后续工程能力是否会被客户混淆。

由此推导，本轮评审重点不是再挑字段细节，而是审查：**客户共鸣、演示闭环、证据可信、能力边界和修改可执行性**。

## 4. 主要优点

- 方向正确。材料把场景 2 定位为“袭击风险上升与防卫准备”，把场景 3 定位为“能源关键设施损伤与恢复监测”，避免了精确预测、打击目标和攻击路径这类高风险表述。
- 主线可串联。场景 2 负责从海上通道风险升高进入准备窗口，场景 3 负责承接风险外溢后的设施损伤、运行影响和恢复监测，具备一条可讲的业务链。
- 数据和本体底盘扎实。对象字典、数据治理表、证据关系、规则设计、评分口径、demo 目录和验收项都已经有雏形，适合作为工程和数据团队的补强底稿。
- 不确定性处理意识较好。材料明确 `visible_at`、支持/反驳证据、数据质量解释、人工复核和未来信息泄露控制，能降低历史回放被质疑为“事后诸葛亮”的风险。

## 5. 主要问题清单

### P1 - 客户故事没有从“现场压力”打透

位置：第 1 节“业务目标”、第 2/3 节业务背景。

问题：材料知道要保护什么，但还没有把“客户为什么今天就需要这个系统”讲到足够具体。当前表达偏抽象，例如“海事、能源、港口和安全保障人员看得懂”“系统能不能在事情变坏之前……”；客户角色、班次压力、误判代价和决策动作还不够清楚。

依据：售前材料的共鸣不是来自“平台能力完整”，而是来自角色压力链：谁在现场、看到什么矛盾信号、如果迟判会损失什么、系统改变哪个动作。当前文档更多是在解释方案应该怎么写，还没有先让客户进入自己的工作现场。

影响：客户可能认可方向，但不一定有“这就是我的问题”的反应；后续演示容易变成能力讲解，而不是业务冲突推动。

建议：在客户版开篇新增 3 个短场景：

- 海事值班主管：夜间收到油轮风险传闻，但 AIS 有缺口、新闻互相矛盾，必须决定是否提升监测和通知港口。
- 港口运营负责人：外海风险升高，担心船期延误、锚地拥堵和保险成本，但不能只靠一条新闻调整安排。
- 能源设施安保负责人：新闻称设施受损，官方又称恢复，必须判断哪一处组件、哪一类服务还需要持续监测。

验证：修改后让非技术同事只读开篇 2 分钟，看能否复述“谁怕什么、系统帮他做什么、最后看到什么结果”。

### P1 - 客户版和内部底稿没有分层

位置：第 1 节、4-8 节。

问题：同一份文档里同时承担客户故事、工程规则、本体字典、数据表设计、目录规划和验收计划，导致读者切换成本高。开篇出现“这两个场景要讲的不是……而是……”“它不能被写成……应该展示的是……”“这篇文档的写法因此分两层”等内部写作说明。

依据：客户材料应呈现业务判断和演示结果；写作意图、工程字段、规则编号和数据目录应进入附录或内部版。否则客户看到的是作者提纲，而不是成熟方案。

影响：材料会显得像内部工作底稿或 AI 辅助生成稿，削弱专业可信度。

建议：拆成两层：

- 客户版正文：业务压力、演示时间线、关键画面、证据矩阵、输出报告、边界说明。
- 内部附录：本体对象、CSV 字段、目录结构、规则权重、数据治理、验收项。

验证：客户版正文不出现“这篇文档怎么写”“不能写成什么”“工程落地应如何分层”这类作者视角句式。

### P1 - 场景 3 缺真实设施样例会阻断客户可信度

位置：第 3 节、第 4.2 节、第 6.3 节、第 7.2 节。

问题：材料自己承认当前 4 张卫星样例图不是能源设施损伤样例，场景 3 还缺能源设施 AOI、组件边界、真实多时相影像、火点基线、运营状态和恢复证据。

依据：设施损伤与恢复监测不是抽象方法展示。客户必须看到“哪个设施、哪个组件、哪期影像、哪条火点/运营证据、为什么支持或反驳恢复判断”。没有真实或高质量替代样例时，只能称为方法演示，不能作为客户主场景承诺。

影响：客户可能质疑“你们只是会画流程图，没有真的做设施监测”。

建议：先冻结一个最小设施包：1 个港口或能源设施、至少 5 个组件、T0/T1/T2 或 Tn、火点或无火点反证、官方/运营状态记录、人工标注说明和退出条件。

验证：演示中任一损伤/恢复判断都能回到具体影像、火点、通告或运营指标。

### P2 - 评分规则缺少客户可解释性

位置：第 4.6 节。

问题：`公开威胁升级 +20`、`快艇集群接近 +25`、`数据质量不足 -10` 便于内部调试，但直接给客户看会被追问权重来源、样本规模、误报率和阈值稳定性。

依据：售前阶段可以使用可解释加权评分，但必须把它定位为 demo v1 规则，不是生产预测模型。客户需要相信每次分数变化对应真实证据，而不是相信某个神秘分数。

影响：评分曲线可能从“透明解释”变成“拍脑袋权重”。

建议：补一条样例评分时间线，逐点说明：新增了哪条证据、证据支持还是反驳、是否有数据质量降权、是否需要人工复核。对外展示时强调“分数是证据组织方式，不是确定性预测”。

验证：隐藏权重数字后，客户仍能通过证据矩阵理解为什么从 `background` 升到 `prepare_defense`。

### P2 - 演示画面和主持人口径不足

位置：第 2.3、3.3、5、7 节。

问题：材料列出了输出项和数据表，但还没有形成“第几分钟看到什么画面、主持人说什么、客户会问什么、系统如何降级回答”的运行脚本。

依据：售前 Demo 的说服力来自可感知动作：风险卡片、地图高亮、证据矩阵、评分时间线、二次确认任务、设施监测卡、报告导出。后台对象和 CSV 目录不能替代画面。

影响：工程和售前会各自理解演示，彩排时容易出现画面与叙事脱节。

建议：新增“演示运行表”，字段包括阶段、画面、触发数据、系统动作、主持人口径、客户可能追问、降级回答。

验证：不看源码和数据表，只看运行表即可完成一次 8-12 分钟彩排。

### P2 - 当前能力、mock 和后续建设边界需要显式矩阵

位置：第 4.1、4.2、8 节。

问题：材料说明了 `doops-dev`、`gintbroker` 和数据中台分工，但没有给客户或售前团队一张“已具备 / 可复用 / 演示替身 / 需后续建设”的能力边界矩阵。

依据：售前可信度不只来自能力强，也来自不乱承诺。涉及卫星任务、真实影像订购、模型识别、生产接口、客户数据接入和规则下发时，必须区分现有能力和演示替身。

影响：客户可能误解当前系统已经实现端到端 L1/L2/L3，后续验收风险上升。

建议：新增能力边界矩阵：

- 已具备：地图展示、多源态势底座、部分新闻/遥测/火点/SAR catalog 能力。
- 可复用：动态本体对象、规则配置、证据链、报告对象。
- 演示替身：冻结数据包、人工标注影像、mock 卫星任务、手工整理事件表。
- 后续建设：真实任务流、模型推理、客户数据接入、权限审计、数据中台增量链路。

验证：每个客户可见动作都能标注其能力来源。

### P3 - 技术命名和目录结构应后移

位置：第 4.3、4.4、4.7、5.1、5.2 节。

问题：对象字典、工程类名、CSV 字段和 demo 包目录很完整，但如果放在主线中，会打断非技术客户阅读。

依据：客户先买业务故事，再追问技术支撑。主线过早技术化，会让客户还没有形成场景共鸣就进入字段解析。

影响：材料对工程团队友好，对售前客户不够友好。

建议：主线只保留中文对象和业务输出，英文类名、字段名、目录结构放入工程附录。

验证：客户版前 5 页不出现大段 CSV 字段、英文类名或目录树。

## 6. 文风与业务共鸣修改规则

以下不是只针对当前几个句子的局部修改，而是后续重写客户版时应遵守的规则。

### 规则 1：先写客户现场，再写系统能力

错误模式：先讲“系统多源融合、动态本体、规则评分、数据治理”。

正确模式：先讲“某个角色在某个时间窗里必须做判断，但现有数据互相矛盾”。

套用方式：每个场景开头都用“角色 + 压力 + 误判代价 + 必须动作”起笔，再引出系统能力。

### 规则 2：每个价值判断都要落到一个动作

错误模式：“提升决策效率”“形成闭环”“增强态势感知”。

正确模式：“从散点新闻和轨迹切换到证据矩阵”“从事后确认切换到提前二次确认任务”“从口头判断切换到可导出报告”。

套用方式：凡是出现“提升、增强、赋能、闭环”，都要追问：客户屏幕上看到什么？谁会收到什么任务？报告里多了哪条证据？

### 规则 3：边界用专门章节讲，正文少用否定式纠偏

错误模式：“不是……而是……”“不能……应该……”连续出现在正文。

正确模式：正文直接讲系统如何做；边界统一放入“演示边界与不做事项”。

套用方式：把内部纠偏句改成正向陈述，把不做事项集中成 5-7 条清单。

### 规则 4：技术细节按“故事 -> 画面 -> 证据 -> 附录”下沉

错误模式：业务背景刚开始就进入类名、字段、目录和规则权重。

正确模式：先讲演示故事和画面，再讲证据矩阵，最后把本体对象、字段和规则放在附录。

套用方式：客户版每个技术表格前都要有一句“客户为什么需要看这个”的解释；不能解释的表格移到内部版。

### 规则 5：不确定性要可见，但不能让故事失焦

错误模式：为了谨慎，把每段都写成“候选、待确认、不能证明”，导致客户只记住系统什么都不能判断。

正确模式：把不确定性组织成下一步动作：二次确认、人工复核、持续监测、报告降级。

套用方式：每个“不确定”后面必须跟一个“系统下一步做什么”。

## 7. 建议修改路径

必须修改：

- 重写开篇 2 页客户主线：角色压力、误判代价、系统动作、最终输出。
- 拆分客户版主线和内部工程附录，删除客户正文中的写作说明和内部纠偏语气。
- 冻结场景 2 至少 2 个事件包，补 `visible_at`、结果确认时间、评分时间线和证据矩阵。
- 冻结场景 3 至少 1 个设施包，补组件、多时相影像、火点/反证、运营状态和恢复退出条件。
- 增加能力边界矩阵，明确现有能力、可复用能力、演示替身和后续建设。

建议修改：

- 给评分规则补一条完整样例，而不是只列加减分。
- 给每个输出卡片补“客户看到什么、系统说明什么、主持人怎么讲”。
- 在数据清单中补 `license`、`display_allowed`、`cache_policy`、`sensitivity_level`、`redaction_rule`。
- 把所有高敏建议固定为保护性动作：提升监测、准备护航/避险、通知海事/港口/能源运营方、调取卫星二次确认、持续监测和报告归档。

可后置：

- 全量自动影像订购和模型推理。

## 8. 后续补强能否复用 `review-driven-plan-refiner`

结论：**可以复用，而且它适合作为下一步修改源方案的主流程；但需要给它补一个“售前演示方案”材料类型或在本仓加项目级适配说明。**

适用原因：

- 当前任务正是“读取评审报告 -> 拆解问题 -> 将合理建议补回目标材料”。
- `review-driven-plan-refiner` 已支持需求/方案分析、技术/架构方案、实施计划、执行交接和评审报告自身，并要求建立“评审意见 -> 文档改动”的映射。
- 本次目标材料不是实施计划，而是售前 Demo 方案；该 skill 当前的自适应定位允许先识别材料类型，再选择补强策略。

使用方式建议：

1. 输入本评审报告作为 review 材料。
2. 定位目标材料为 `devdoc/DYINT场景2-3Demo数据规则与补强方案.md`。
3. 将目标材料类型标记为“售前演示方案 / Demo story / 客户场景需求包”，不要按技术实施计划处理。
4. 逐条建立处理状态：`采纳`、`部分采纳`、`暂缓`、`不采纳/有异议`、`材料缺口`。
5. 优先改源方案的客户主线、演示故事、画面脚本、证据矩阵和边界说明；本体、字段和目录结构只做重排或后移，不要为了“客户化”删除工程可执行信息。

建议对 `review-driven-plan-refiner` 做的增强：

- 新增目标材料类型：`售前演示方案 / Demo story / 客户场景需求包`。
- 新增补强策略：客户角色、现场压力、传统失效、误判代价、演示时间线、可见画面、主持人口径、证据矩阵、演示替身、能力边界和客户版/内部版分层。
- 新增文风吸收规则：把“内部写作说明、作者自评、否定式纠偏、AI 模板腔、过早技术化”转成客户现场表达。
- 新增输出要求：必须列出“客户版新增/改写章节”“内部附录保留章节”“暂缓的数据或资产缺口”“复审条件”。
- 新增与 `presales-demo-review` 的关系：先用 `presales-demo-review` 产出评审报告，再用 `review-driven-plan-refiner` 吸收评审意见改源材料；改完后再用 `presales-demo-review` 复审售前效果。

本轮不建议直接修改全局 `review-driven-plan-refiner` skill。原因是这属于跨项目通用 skill 的能力扩展，需要单独确认改造范围和回归；当前更稳妥的是先在本评审报告里明确适配规则，后续实际改源方案时按这些规则约束执行。
