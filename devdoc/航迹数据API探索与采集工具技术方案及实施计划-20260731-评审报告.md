## 1. Gate 与一句话结论

8. 方案没有 authorization/adoption/checksum/CAS 或特殊 Git 协议；当前 T0～T4 五阶段和后续 M1 Gate 复杂度已基本合理。

## 5. 当前问题

### P0

无。

### P1：本地高权限 API 缺少 Host/Origin 边界，无法防 DNS rebinding

**来源判断：** 原方案安全边界的遗漏；不是 `909e3e0` 整改引入。此前评审关注上游明文链路，未覆盖浏览器到本地服务的 DNS rebinding 路径。

**依据：** Go 服务持有上游凭据并能返回原始航迹数据，默认监听回环地址。方案要求“同源策略”和 CSP，但没有限定请求 `Host`，也没有校验浏览器 `Origin`。恶意网页可以使用攻击者控制的域名和 DNS rebinding 把后续请求解析到 `127.0.0.1:8080`；对浏览器而言请求仍是攻击者 origin，本地 Go 服务若接受该 Host，就会把 `/api/v1` 响应返回给攻击页面。同源策略不能替服务端识别这一点。

**失败模式与影响：** 用户访问恶意页面时，页面可借本机 `dy-track-explorer` 发起 ADS-B/AIS 查询、消耗上游配额并读取可能敏感的原始响应；这绕过了“只有本机/受信用户可达”的首期假设。浏览器看不到上游 token 并不等于本地代理没有被滥用。

**最小修改：** 不引入自有账号系统或 CSRF 状态机，只增加薄中间件和固定配置：

1. 默认只允许 `Host` 为监听端口上的 `localhost`、`127.0.0.1`、`[::1]`；其他 Host 在进入 handler 前返回 403。
2. 对浏览器 `/api/v1` 请求校验非空 `Origin` 必须等于配置的公开 origin；CLI/cURL 可允许无 Origin，但仍受 Host 校验。首期不启用 CORS。
3. 反向代理部署时使用单一显式 `PUBLIC_ORIGIN`/allowed host 配置，并要求代理覆盖 Host；未配置却监听非回环地址时 fail closed，不靠任意 `X-Forwarded-*` 推断信任。
4. 增加 `Host=attacker.example`、`Origin=http://attacker.example`、合法 localhost、无 Origin CLI 和受控反向代理五类测试。

**通过判定：** 恶意 Host 或 Origin 在上游 client 被调用前即被拒绝，fake upstream 调用次数为 0；合法本机和已配置反向代理 origin 正常完成查询。

### P2：complete 只有记录数上限，没有聚合响应字节上限

**依据：** `MAX_RESPONSE_BYTES` 只限制每次上游响应，`MAX_COMPLETE_RECORDS` 只限制唯一记录数。complete 可接受多个切片，单条记录也可能包含异常大字符串；最终合并 JSON 和序列化副本没有总字节预算。

**失败模式与影响：** 多个切片分别低于 20 MiB，但合并后可能显著超过浏览器或进程的合理内存预算；20,000 条记录也不能证明响应体足够小。结果可能在服务端 marshal 或浏览器渲染阶段耗尽内存。

**最小修改：** 增加 `MAX_COMPLETE_BYTES`，在接受切片和追加记录时累计规范化内容字节；超过上限返回 `COMPLETE_RESULT_TOO_LARGE` 且不返回部分 content。最终响应编码仍需有对应上限测试。默认值按实际样本留余量即可，不需要动态内存治理。

**通过判定：** fake 构造“记录数未超限但聚合字节超限”场景，服务明确失败、不返回部分结果；正常 20,000 条以内的小记录仍可完成。
