## 1. Gate 与一句话结论

上一轮的实现仓归属、`best_effort` 语义、长期 `id` Gate 和 `go:embed` 冷构建路径已经实质补齐，Go/React 单体方向仍然成立；但当前版本不能直接进入 T0，因为**整改把仓库归属扩大成了会立即阻断执行的 GitHub/GHCR 权限门禁、明文 HTTP 的风险接受和代理路径仍未形成可验证闭环、`direct` 与多切片 `complete` 共用的响应示例无法表达真实执行结果**。另有两项整改引入的非必要复杂度应删除，而不是继续补协议。

## 2. 审查范围和关键事实

本轮重新读取了最新源方案、上一版 sibling 评审报告、接口实测指南、交互 Mock、仓库规则、`1565f87` 完整 delta，以及计划指定的 `checkpointed-plan-executor` 授权边界。

关键事实：

1. 源方案已把运行代码固定到独立 `isxylands/dy-track-explorer`，`dy-inta` 继续作为文档真源，仓库职责冲突已关闭。
2. 现场只读检查确认 `/Users/liushen/Documents/githubDevs/dy-track-explorer` 不存在；未认证的 GitHub 远端查询返回 repository not found。方案同时要求远端、PR、GitHub Actions、GHCR 和维护权限任一缺失都停止 T0。
3. `checkpointed-plan-executor` 允许计划内普通 commit/push、既有 CI 和测试环境动作，但不自动授权创建外部仓库、修改团队/权限或配置新的 CI/包权限。按当前入口执行会在 T0 第一步停止，连本地骨架都不能建立。
4. 上游只提供 `http://`，登录 URL 含用户名、密码摘要和时间戳，业务 header 含 token。方案已做到默认拒绝明文地址、显式 insecure 开关和不宣称传输安全，但“用户已接受”没有可追踪的日期、适用环境或确认记录。
5. Go `net/http` 的常见默认 transport 会使用 `HTTP_PROXY`、`HTTPS_PROXY` 和 `NO_PROXY`。方案声称“单跳受控出口、避免额外代理日志”，却没有固定 `Transport.Proxy` 策略或代理负向测试；在存在 `HTTP_PROXY` 的环境里，登录 query 仍可能经过并记录在额外代理。
6. `complete` 会产生多个上游请求、多个 HTTP/业务状态和多个 `requestid`，并形成合并结果；当前响应示例只有一个 `transport`、一个 `upstream.body`，同时又声称该 body 保留原始上游 JSON，无法同时表达多切片原文与合并结果。
7. 方案没有新增 authorization/adoption/checksum/CAS 或特殊 Git 状态机；两仓分别提交并用普通 commit/CI 证据关联是合理的，不需要新增跨仓原子协议。

## 4. 应保留的设计

1. 保留独立实现仓，但先以唯一的本地 Git 仓启动 T0；不要回退到 `dy-inta` 或临时换到其他运行仓。
2. 保留 Go 模块化单体、React SPA、同源单端口、固定 dataset allowlist 和后端凭据边界。
3. 保留 `direct` 与 `complete`，并保留所有 `complete` 固定 `best_effort` 和永久历史可变警告。
4. 保留单并发、超时、响应限长、`604` 单次刷新重放、fake upstream、race、Playwright、冷启动和真实低频 smoke。
5. 保留 `internal/webassets/dist`、明确构建顺序和无残留 dist 冷构建验证。
6. 保留长期 `id` 稳定性、SQLite/NFS、数据许可和时区为 M1 Gate，不提前实现存储。
7. 保留两仓普通 commit/CI 引用，不增加自研跨仓状态协议。

### P1-1：仓库归属整改被扩大成不必要且当前不可达的 T0 外部权限门禁

**来源判断：** 上一轮整改引入。

**依据：** 独立仓选型本身已解决代码落点问题，但第 6、7、9、10 节又要求 GitHub 远端、PR、Actions、GHCR、Release、CODEOWNERS 和团队权限在 T0 前全部成立。当前本地目录和可见远端均不存在；执行器授权边界也不覆盖新建外部仓、团队/包权限配置。

**失败模式与影响：** 用户按文末入口启动计划后，执行器必须在 T0 第一步停止请求外部权限，无法产生 Go/React 骨架和本地测试反馈。GHCR 和 Release 明明到 T3/发布时才使用，却提前阻断 T0。

**最小修改：** 保留唯一实现路径，但把 T0 分成普通本地起步和后续外部发布准备：

- T0 只要求创建 `/Users/liushen/Documents/githubDevs/dy-track-explorer` 本地 Git 仓、写 README 中的维护边界并完成本地 `make verify`；本地目录非空或已有其他 Git 根才停止。
- 远端创建、团队/PR 权限和 Actions 作为首次 push/CI 前置；需要外部写操作时由用户单独明确授权或由仓库管理员完成。
- GHCR、Release artifact、`amd64/arm64` 和包权限移到 T3/发布 Gate；首期若只交付本地二进制，不应因 GHCR 不可用阻断功能实现。
- `CODEOWNERS` 仅在真实账号/团队已知且远端支持时创建，不用占位“DYINT 工程实施团队”冒充可执行配置。

**通过判定：** 在没有远端和 GHCR 的当前环境中，T0 仍能建立本地仓、完成骨架与本地验证；首次外部写操作前有单独、明确、可执行的权限分支。

### P1-2：明文 HTTP 的“已接受”缺少证据，且单跳出口未由客户端合同保证

**来源判断：** 上一轮 P1-2 只关闭了一部分；insecure 开关有效，但风险接受与代理路径仍缺证据。

**依据：** 文档多处直接写“用户已接受”，但没有记录确认日期、适用环境、有效期或执行记录入口。与此同时，客户端基于 Go `net/http`，方案未规定 `Transport.Proxy`；若使用常见的 `ProxyFromEnvironment`，`HTTP_PROXY` 可让登录 query、token 和明文响应经过额外代理，与“单跳受控出口、避免代理日志”矛盾。

**失败模式与影响：** T4 可以仅凭配置文件中的 `TRSDH_ALLOW_INSECURE_HTTP=true` 执行真实登录，却无法证明风险由有权人员针对该环境接受；企业环境的 ambient proxy 还可能额外记录可重放 token 和敏感航迹。

**最小修改：** 不把提供方 HTTPS 改造重新设为本项目 Gate，只补使用方可控闭环：

1. 删除无依据的“用户已接受”既成事实，改为“T4 首次真实调用前，由执行请求或计划执行记录明确确认明文风险、适用网络和有效期”；没有确认只跑 fake。
2. 固定上游 client 的 proxy 合同：默认 `Transport.Proxy=nil` 直连；如现场必须使用受控代理，新增单一显式配置并禁止从 ambient `HTTP_PROXY` 静默继承。
3. 增加负向测试：设置捕获型 `HTTP_PROXY` 后，默认 client 不访问该代理；显式代理分支只记录 scheme/host/port，不记录登录 query、token 或响应体。

**通过判定：** T4 证据同时包含风险接受记录、部署网络边界和 proxy 行为；三项任一缺失时不使用真实凭据。

### P1-3：单一响应示例无法同时承载 `direct` 原始响应和 `complete` 多切片结果

**来源判断：** 原方案已有的跨端合同缺口，上一轮补强 `complete` 元数据后仍未关闭。

**依据：** 请求示例是 `mode=direct`，响应却带 `completeness=best_effort`、切片和历史可变警告。结构只有一个 `transport`、一个 `upstream.requestId` 和一个 `upstream.body`；但 `complete` 会发出多个请求并合并 content。文档又要求 `upstream.body` 是不改写的原始 JSON，二者不能同时成立。

**失败模式与影响：** T0 要冻结 OpenAPI 时，后端和前端必须临时决定：保留哪一个切片的原始 body/requestid、是否伪造合并后的“上游 body”、切片失败时整体还是部分成功。不同选择会直接改变 UI、错误处理和测试，无法靠实现期小修消除。

**最小修改：** 在 OpenAPI 中明确两个响应分支，保持最小合同：

- `direct`：返回一次 `transport` 和未经改写的 `upstream.body`；完整性字段为 `not_applicable` 或不返回。
- `complete`：返回 `result.content`、固定 `best_effort`、合并计数和 `slices[]`；每片只保留必要的范围、HTTP/业务码、`requestid`、计数、重试和错误摘要，不把合并结果包装成原始上游 body。
- 明确 fail-fast：任一必要切片最终失败则整次 `complete` 失败，不返回看似成功的部分结果；如确需部分结果，必须显式 `status=partial`，首期不建议增加该分支。

**通过判定：** OpenAPI 对两种 mode 有互斥、可生成类型的响应 schema；fake 多切片用例能断言多个 requestid、合并结果、任一切片失败和单秒爆量路径。

### P2-1：查询/结果指纹与浏览器会话比较属于整改引入的补偿性复杂度，应删除

**依据：** 固定 `best_effort` 和永久 `UPSTREAM_MUTABLE_HISTORY` 已足以防止用户把结果理解成权威快照。新增的 `resultFingerprint` 只基于 ID 集，同 ID 内容修订时不会变化；会话内基线又在刷新后丢失。

**影响：** 该机制增加规范化、哈希、前端会话状态和 UI 分支，却不能可靠证明结果稳定，容易把“指纹没变”误读成数据没变。

**最小修改：** 从首期 API、S5、T1、T2 和 UI 删除 query/result fingerprint 与 `UPSTREAM_RESULT_CHANGED` 产品功能。T4 仍可在验收脚本中比较两次 ID 集和必要字段，仅作为上游可变性的测试证据，不改变 API 完整性等级。

**通过判定：** 首期 UI 始终只显示 `best_effort` 和永久历史可变警告；刷新、首次查询和重复查询没有额外“稳定/变化”状态机。

### P2-2：合法的 8 位日期输入与秒级二分合同不完整

**依据：** 上游允许 `yyyyMMdd` 或 `yyyyMMddHHmmss`，方案也只说拒绝非法格式；`complete` 却依赖秒级中点和 `+1 second`，没有定义 8 位起止日期怎样规范化。

**影响：** 同一天的 `20260729` 可能被解析成两个午夜点，只查询一秒，也可能被扩成全天；前后端自行选择会造成查询指纹、预览和真实范围不一致。

**最小修改：** 首期最简单的做法是 `complete` 只接受 14 位时间；`direct` 可原样允许 8/14 位。若要支持日期级尽力查询，则明确 start 扩为 `00:00:00`、end 扩为 `23:59:59`，并在实际请求预览中展示规范化后的值。

**通过判定：** 契约测试覆盖 8/14 位、同日、跨日、非法日期和反向窗口，UI 预览与后端实际发送值一致。
