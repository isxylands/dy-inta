## 1. Gate 与一句话结论

方案的产品目标、Go/React 单体架构、凭据留在后端、HTTP/业务码双重判定、时间切片、测试分层和阶段回滚总体合理，技术栈版本也与当前官方稳定线一致；但目前不能直接交给执行器，因为**运行代码落点违反本仓既定边界、明文上游链路未进入安全 Gate、一次 `complete` 查询被错误表述和验收为“历史不漏采”**。三项均会改变实施或验收结论，修正后再进入 T0。

## 2. 审查范围和关键事实

本轮重读了目标方案、接口实测指南、交互 Mock、仓库 `README.md`、`AGENTS.md` 和目标文档最新 Git 提交。当前没有已有 sibling 评审报告。

已确认事实：

1. `dy-inta` 的 `README.md` 与 `AGENTS.md` 都把本仓定义为需求、评估、方案和交接文档仓，明确“不是运行系统源码仓”；而方案直接决定在本仓新增 `track-explorer/` 运行模块，尚未给出仓库定位变更或独立实现仓选择依据。
2. 上游实测基址是 `http://dh.trs.cn/datas/api`。登录请求把用户名、时间戳和密码摘要放在 URL query，业务请求把 token 放在 header；当前方案只覆盖浏览器、日志和 Git 泄密，没有覆盖链路窃听、代理日志、重放与原始航迹明文传输。
3. 上游历史查询已实测出现总数变化、重复页、补录或重整，且不支持 `id` 参与稳定排序。时间切片能避免普通 `pageNum++` 的确定性缺陷，但单次结果仍不能证明历史数据没有后补或重整。
4. `id` 只在本轮样本内确认唯一，尚未确认跨时间、跨任务长期稳定。首期内存去重可以先使用，但未来 `UNIQUE(dataset, source_id)` 不能在未验证前作为最终幂等合同。
5. 截至本次评审，Go 1.26、Vite 8.1、Node.js 24 LTS 和 React Router 8.3 均有官方当前版本依据，技术栈版本不是当前 Gate：
   - [Go Release History](https://go.dev/doc/devel/release)
   - [Vite 8.1](https://vite.dev/blog/announcing-vite8-1)
   - [Node.js Releases](https://nodejs.org/en/about/previous-releases)
   - [React Router Releases](https://reactrouter.com/start/start/changelog)

复杂度盘点：方案没有引入自研授权状态机、adoption、descriptor/checksum、终态 CAS 或特殊 Git 协议；这些内容不需要新增。T0～T4 五阶段与当前标准风险基本匹配。

## 4. 应保留的设计

1. 保留 Go 模块化单体 + React SPA + 单端口交付，不拆微服务，不提前创建空的 `jobs`、`storage` 包。
2. 保留 `direct` 与 `complete` 两种语义，但把 `complete` 准确定义为“按当前多次切片响应尽力取得的去重结果”，不要命名或展示成权威完整快照。
3. 保留固定 dataset allowlist、浏览器不可指定任意 URL、凭据仅在后端、`604` 单次刷新重放、响应限长、单并发和任务 deadline。
4. 保留 catalog 单一来源、字段确认状态、原始时间字符串、未知单位/时区提示和原始响应不擅自改写。
5. 保留 fake upstream、race、Playwright、冷启动和真实低频 smoke 的分层验证；真实 API 不做自动压力测试。
6. 保留 T0～T4 的阶段结构和按阶段回退，不新增评审状态机或特殊 Git 协议。

## 5. 当前问题

### P0

无。

### P1-1：运行模块落点与仓库既定定位冲突

**依据：** 方案第 1、3.1、6、13 节把“当前只有文档”解释为在本仓新增 `track-explorer/` 的理由；但 `README.md` 和 `AGENTS.md` 明确本仓不是运行系统源码仓，`README.md` 只要求先决定改造 `gintbroker` 还是新建服务/模块。

**失败模式与影响：** 直接执行会把文档真源与运行代码、Node/Go 依赖、CI、镜像和发布责任混在一起，同时绕过实现仓选择。后续执行器也无法从现有规则判断 CI、制品、部署环境和维护团队。

**最小修改：** 在 T0 前增加一个仓库落点决策，候选只需比较：独立 `track-explorer` 仓、现有运行仓中的独立模块、明确重定位后的 `dy-inta`。默认建议保留 `dy-inta` 为方案真源，在独立运行仓落地；若确实选择本仓，必须同步修改 `README.md`、`AGENTS.md`、CI/制品归属和维护边界，不能只加目录。

**通过判定：** 文档给出唯一目标仓绝对路径或仓名、代码所有权、CI 入口、镜像/二进制归档位置；所有 T0～T4 命令和文件路径据此更新，不再与仓库规则冲突。

### P1-2：认证与敏感航迹仍可能通过明文 HTTP 泄露或被重放

**依据：** 接口指南确认的基址是 `http://`，登录 query 含用户名、密码摘要和时间戳，业务 header 含 token。方案 S3 只检查浏览器、页面、日志、错误和 Git，安全章节也只约束应用内 secret 与浏览器入口。

**失败模式与影响：** 网络中间人、出口代理或透明网关可读取/记录登录 URL、token 和航迹响应，并在有效期内重放 token。MD5 摘要不是传输加密；即使原始密码不出现，仍不能把链路称为认证安全。

**最小修改：** 将“上游传输保护”提升为真实调用前 Gate：优先确认官方 HTTPS 端点及证书校验；否则要求受控 VPN/专线/反向 TLS 隧道，并明确终止点、访问控制和日志脱敏。客户端默认拒绝明文远端地址；如仅为受控验证临时允许，必须显式开关、限定网络和时间、记录风险接受人，且不得作为生产默认值。

**通过判定：** 在 T4 环境抓取脱敏连接元数据，证明上游链路使用经校验证书的 TLS，或有经批准的等效受控隧道；失败时只保留 fake 验证，不执行真实凭据登录。

### P1-3：`complete` 的措施和验证不能支持“历史查询不漏采”结论

**依据：** 接口指南已确认历史总数会变化且存在补录/重整；方案却把一次切片、`id` 去重和 fake 用例标为“历史查询不漏采 covered”。回看最近片段、每日 24～48 小时回看和总量核对只存在于后续持久化方案，首期 T1/T4 没有对应措施。

**失败模式与影响：** 某片调用时 `totalPages == 1`，稍后上游补入新记录；算法会把当次结果标成完整成功。fake 测试仍全部通过，用户却可能把“complete”结果用于需要完整性的分析。

**最小修改：** 首期不要承诺“历史不漏采”。把 S5、矩阵、API 返回和 UI 文案改为“避免普通分页缺陷的尽力查询”；响应增加查询时点、切片范围、每片返回计数、去重计数和 `completeness=best_effort`/警告。T4 对同一受控窗口间隔重跑并比较 ID 集与总数，变化时必须展示不稳定提示。真正的可恢复完整采集继续由 M1 的 `loadTime` 水位线、重叠回看、持久化和总量核对承担。

**通过判定：** fake 用例能证明切片算法不越界、不普通翻页；真实重复查询若结果变化会显式降级，任何页面、API 或文档都不把单次结果称为权威完整快照。

### P2-1：长期幂等键与冲突处置尚未建立证据

**依据：** 接口指南只确认 `id` 在本轮样本内唯一；方案后续存储直接使用 `UNIQUE(dataset, source_id)` 并执行覆盖写。

**失败模式与影响：** 若 `id` 被复用、修订或不同记录共享标识，覆盖写会静默丢数据；若同一观测被重新分配 `id`，则会重复保存。

**最小修改：** 把 `id` 稳定性验证加入 M1 Gate：跨日期、重跑窗口、ADS-B/AIS 分别统计 `id` 与关键字段关系；定义“同 ID 不同对象/时间/坐标”的冲突表或阻断策略。证据成立后再采用唯一约束，否则使用版本化 Raw 和经验证的复合业务键，不能静默覆盖。

**通过判定：** 有跨窗口样本报告和冲突 fixture；重跑幂等测试同时覆盖同 ID 同内容、同 ID 内容更新、同 ID 关键身份冲突。

### P2-2：首期构建合同缺少 `go:embed` 产物落点

**依据：** 目录把 Go 包与 `web/dist` 分开，方案只写“使用 `go:embed`”，没有说明 embed 指令所在包、前端产物复制位置或构建顺序。Go embed pattern 不能通过 `..` 引用包目录外文件。

**失败模式与影响：** 实施者把 embed 文件放在 `cmd/server` 或 `internal/httpapi` 后直接引用 `web/dist` 会构建失败；本地开发可能依赖残留 dist，冷构建才暴露。

**最小修改：** 在 T3 固定一种做法：例如将 `npm run build` 输出/复制到 `internal/webassets/dist`，由该包 embed，并让 `make verify` 先清理旧产物、前端构建、再 Go build；或把可 embed 的 Go 包与产物放在同一目录树。

**通过判定：** 从无 `dist` 的干净工作树执行一次冷构建，单二进制可加载 SPA，且改动前端后重新构建能更新嵌入内容。

## 6. 最小修改路径和验证

不需要重写架构，按以下顺序修正文档即可：

1. **先定实现仓。** 在第 1、3.1、6、9、13、14 节统一代码落点、CI、制品和维护边界。
2. **补上游传输 Gate。** 在第 2.2、5.5、5.8、7、T1、T4、验证矩阵和风险表中加入 TLS/受控隧道及 fail-closed 行为。
3. **校正 `complete` 语义。** 删除“历史不漏采”绝对承诺，明确单次结果为 `best_effort`；加入真实窗口重复查询差异诊断，把可恢复完整采集留给 M1。
4. **补 M1 幂等 Gate。** 在第 7、8.2 和后续验证中增加 `id` 稳定性与冲突处置，不提前承诺 `UNIQUE(dataset, source_id)` 一定安全。
5. **固定 embed 冷构建路径。** 只补一个明确实现，不新增多套兼容方案。
