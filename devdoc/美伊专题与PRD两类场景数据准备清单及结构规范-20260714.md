## 一、先说结论

| 场景 | 当前基础 | 能否直接完成演示 | 主要缺口 |
|---|---|---|---|
| 在线 Mock 美伊专题 | 已有 25 条新闻、59 条 AIS、28 条 ADS-B，以及部分基地、装备、组织和地理数据 | 可以支撑基础列表、地图点位和简单时间线；不能稳定支撑四类情报统计、证据说明和详情回溯 | 缺统一主键、专题分类结果、来源溯源、实体关联、事件归并、连续轨迹和统计口径 |
| PRD 场景 1：商船安全事件多源验证 | 新闻、AIS、ADS-B 和规则库均有样例 | 可做素材展示；尚不能完整演示“发现—核验—研判—报告” | 缺确定的事件包、时间窗口、异常结果、证据关系、核验矩阵、风险结论和报告数据 |
| PRD 场景 2：关键设施持续监测 | 有设施基础库和少量油气、电力、港口数据 | 暂不能形成完整场景 | 缺选定设施、设施范围与组成、基线、状态变化、影响评估、监测任务和报告数据 |

当前最需要补的不是更多百科条目，而是把已有素材加工成可关联、可核验、可追溯的场景数据包。

## 二、统一的数据交付要求

三类场景共用一套基础字段。新闻、轨迹点、设施、事件、规则结果等每条记录都应带以下“数据外壳”。

| 字段 | 必填 | 说明 | 示例 |
|---|---:|---|---|
| `record_id` | 是 | 全局唯一 ID，交付后不得变化 | `obs_news_0001` |
| `scenario_id` | 是 | 所属场景 | `us_iran_topic`、`prd_s1`、`prd_s2` |
| `data_type` | 是 | 数据类型 | `news`、`ais`、`adsb`、`facility`、`event` |
| `data_class` | 是 | 数据属性 | `REAL_LIVE`、`REAL_FROZEN`、`DERIVED_SAMPLE`、`SIMULATED` |
| `source_id`、`source_name` | 是 | 来源唯一 ID 和名称，不能把多个来源写在一个单元格 | `src_reuters`、`Reuters` |
| `source_url_or_reference` | 是 | 原始链接、文件编号或内部引用 | 原文 URL 或 `file://ref/...` |
| `observed_at` | 按类型 | 事件实际发生或对象被观测的时间 | ISO 8601，统一 UTC |
| `published_at` | 按类型 | 来源发布时间 | ISO 8601，统一 UTC |
| `captured_at` | 是 | 本系统采集时间 | ISO 8601，统一 UTC |
| `visible_from` | 是 | 演示中最早可见时间，防止“提前看到未来数据” | ISO 8601，统一 UTC |
| `geometry` | 涉及时空数据必填 | GeoJSON，坐标统一 WGS84 | `Point`、`LineString`、`Polygon` |
| `transform_note` | 是 | 清洗、翻译、摘要、脱敏、聚合等处理说明 | `中文标题为人工翻译` |
| `license_or_display_note` | 是 | 使用和展示限制 | `公开来源，仅限内部演示` |
| `content_sha256` | 是 | 原始内容或交付文件哈希 | 64 位 SHA-256 |
| `quality_status` | 是 | 质量状态 | `verified`、`reviewed`、`unverified` |
| `raw_ref` | 是 | 指向原始数据，不复制大文件 | 原文件路径、对象存储 URI |
| `schema_version` | 是 | 数据结构版本 | `1.0` |

统一约束：

- 一个来源一条记录。转载、转述和联合来源必须拆开，并通过 `repost_of` 或 `source_lineage_id` 表示继承关系。
- “来源说了什么”和“系统判断是什么”分开存。原始观察进入 `observations`，系统结论进入 `events`、`anomalies` 或 `claims`。
- 时间统一使用 ISO 8601；存储使用 UTC，页面可转换为北京时间。
- 经纬度统一 WGS84。区域用 Polygon，航线用 LineString，不用文字地点代替空间对象。
- 所有派生结果保留生成规则、规则版本和输入记录 ID。
- 对外演示不提供实时精确军事部署或打击目标数据；必要时按区域聚合、延迟展示或降低坐标精度。

## 三、在线 Mock 美伊专题所需数据

美伊专题页面包括四类情报卡片、7 日趋势、地图、时间线、详情和历史回溯。数据不能只按关键词命中，必须给出明确分类结果和依据。

### 3.1 专题情报条目 `topic_intel_items`

四类数据统一入表：

| `category_code` | 内容范围 | 最低准备量 |
|---|---|---:|
| `conflict_intel` | 袭击、冲突、停火、声明、伤亡、制裁及谈判进展 | 至少 5 条，建议 10 条 |
| `key_facility` | 基地、核设施、港口、雷达、指挥节点及状态变化 | 至少 5 条，建议 10 条 |
| `vessel_activity` | 军舰、海警、辅助船、商船的活动及相关公开报道 | 至少 5 条，建议 10 条 |
| `air_activity` | 军机、无人机、空袭、侦察和空中支援活动 | 至少 5 条，建议 10 条 |

每条至少包含：

```text
item_id, scenario_id, category_code, title_original, title_zh,
summary_original, summary_zh, language, source_id, source_url,
published_at, captured_at, visible_from, event_time_start, event_time_end,
location_text, geometry, entity_ids[], claim_ids[], risk_level,
confidence, confidence_reason, decision, evidence_record_ids[],
data_class, transform_note, license_or_display_note, content_sha256
```

补充要求：

- `decision` 取值：`confirmed`、`probable`、`unconfirmed`、`refuted`。
- 同一条信息可命中多类，但必须有一个 `is_primary=true` 的主分类。
- 国家、人物、机构等宽泛实体不能单独作为专题命中依据；至少还要有动作、地点、对象或时间证据。
- 7 日趋势直接按 `event_time_start + category_code + decision` 统计，列表和卡片必须共用同一筛选口径。

### 3.2 实体主数据 `entities` 与别名 `entity_aliases`

用于把新闻、轨迹、设施和事件连到同一个对象。

```text
entity_id, entity_type, canonical_name, name_zh, country_code,
organization_id, identifiers{}, aliases[], description, source_refs[],
valid_from, valid_to, quality_status
```

需优先补齐的实体包括：美国中央司令部、伊朗伊斯兰革命卫队、美国第五舰队、伊朗武装力量、霍尔木兹海峡、阿曼湾、波斯湾、巴林、卡塔尔、科威特、纳坦兹、德黑兰，以及样例中出现的航母、军机、商船和机构。

关键标识不能只靠名称：

- 船舶：`MMSI`、`IMO`、呼号、舷号。
- 飞机：`ICAO24`、注册号、呼号。
- 设施：内部 `facility_id`、公开名称、别名、所属机构和空间范围。
- 组织：标准名称、简称、上下级关系和国家。

### 3.3 AIS 数据

分为船舶主表和轨迹点表。

`vessels.csv`：

```text
vessel_id, mmsi, imo, name, name_zh, callsign, hull_number,
ship_type, flag, owner_operator_id, length_m, width_m,
identity_confidence, source_refs[], risk_tags[]
```

`ais_observations.csv`：

```text
observation_id, vessel_id, observed_at, received_at, latitude, longitude,
sog_kn, cog_deg, heading_deg, navigation_status, position_accuracy,
receiver_or_provider, source_record_id, quality_flags[], scenario_id,
data_class, visible_from
```

最低交付要求：

- 选定演示事件后，准备事件前后至少 7 天的连续轨迹；不能只给若干离散点。
- 每个轨迹点必须能关联到船舶主表，重复 MMSI、名称冲突需在 `identity_resolution.csv` 中说明。
- 需要提供缺报、异常停留、偏航、接近等派生结果，但派生结果不能混在原始 AIS 表中。

### 3.4 ADS-B 数据

`aircraft.csv`：

```text
aircraft_id, icao24, registration, callsign, aircraft_type,
operator_id, country_code, identity_confidence, source_refs[], risk_tags[]
```

`adsb_observations.csv`：

```text
observation_id, aircraft_id, observed_at, received_at, latitude, longitude,
altitude_ft, ground_speed_kn, track_deg, vertical_rate_fpm,
on_ground, squawk, position_quality, receiver_or_provider,
source_record_id, quality_flags[], scenario_id, data_class, visible_from
```

最低交付要求：

- 轨迹点按 `aircraft_id + observed_at` 排序后可形成有效航迹。
- 明确接收源和定位质量；不能把单点出现直接解释成完整活动。
- 侦察、盘旋、抵近、编队等属于规则结果，单独进入 `anomalies.csv`。

### 3.5 设施与专题区域

`facilities.geojson`：

```text
facility_id, facility_type, name, name_zh, aliases[], operator_id,
country_code, geometry, geometry_level, criticality, service_tags[],
status, source_refs[], valid_from, quality_status
```

`aois.geojson`：

```text
aoi_id, scenario_id, name, aoi_type, geometry, country_code,
importance, display_zoom, coordinate_precision_policy,
source_refs[], valid_from
```

美伊专题至少准备：霍尔木兹海峡、阿曼湾、波斯湾，以及选定港口、基地和重点设施的区域范围。设施不能只有名称和介绍，至少要有稳定 ID、类型、所属机构、位置、来源和有效期。

### 3.6 专题匹配和证据关系

`topic_category_matches.jsonl`：

```text
match_id, topic_id, subject_kind, subject_id, category_code,
is_primary, decision, confidence, evidence_record_ids[],
matched_entity_ids[], matched_action, matched_location_id,
rule_id, rule_version, event_time, geometry, created_at
```

`subject_kind` 至少支持 `source_item`、`live_entity`、`event`。该表是四类卡片、趋势图和详情页统计一致的关键，不能由前端临时拼接。

## 四、PRD 场景 1：商船安全事件多源验证

场景目标是完整演示：风险信号出现后，系统调取船舶轨迹、公开消息和相关活动，形成核验结论与处置建议。

### 4.1 先确定一个事件包

数据团队必须先冻结一个明确事件，不能把不同月份、不同海域的样例拼成一条事件链。

`event.json`：

```text
event_id, scenario_id, event_type, title, time_window,
location_id, geometry, involved_entity_ids[], affected_vessel_ids[],
status, severity, confidence, summary, created_from_record_ids[],
as_of, visible_from, data_class
```

事件包需要明确：

- 一艘主船或一组关联船舶。
- 一个连续的事件时间窗口和一个明确海域。
- 至少两个相互独立的公开信息来源。
- 一段可复现的 AIS 轨迹；ADS-B 作为辅助证据时再纳入。
- 一项可解释的异常或风险信号。
- 最终核验结论、置信度和报告。

### 4.2 观察、主张和证据

`observations.jsonl`：

```text
observation_id, source_id, source_type, observed_at, collected_at,
location_id, geometry, raw_ref, original_text, normalized_text,
extraction_method, extracted_entity_ids[], quality_status, confidence
```

`claims.jsonl`：

```text
claim_id, event_id, claim_type, subject_id, predicate, object,
time_window, location_id, asserted_by_source_ids[], status,
confidence, rationale, created_at
```

`evidence_links.jsonl`：

```text
evidence_link_id, event_id, claim_id, evidence_record_id,
relation, supports_or_refutes, weight, independence_group,
rationale, created_at
```

其中 `supports_or_refutes` 取值 `supports`、`refutes`、`neutral`；转载同源材料必须使用同一个 `independence_group`，避免被重复计权。

### 4.3 异常和威胁信号

`anomalies.jsonl`：

```text
anomaly_id, event_id, object_id, anomaly_type, detected_at,
time_window, geometry, baseline_ref, observed_value, threshold,
severity, confidence, input_record_ids[], rule_id, rule_version,
explanation, review_status
```

建议优先准备的结果：异常停留、偏离常用航线、异常接近、轨迹中断、快速小艇聚集、相关空中活动。每个结果必须能回到具体输入记录，不能只写“系统发现异常”。

### 4.4 核验矩阵、风险评估和报告

`verification_matrix.json`：

```text
event_id, claim_rows[{claim_id, evidence_ids[], source_count,
independent_source_count, supports_count, refutes_count,
verification_status, analyst_note}], generated_at
```

`risk_assessment.json`：

```text
assessment_id, event_id, assessed_at, likelihood, impact,
risk_level, affected_objects[], key_factors[], uncertainties[],
recommended_actions[], evidence_ids[], analyst_or_rule, version
```

`report.json`：

```text
report_id, event_id, title, executive_summary, event_timeline[],
verified_findings[], unverified_claims[], risk_assessment_id,
recommended_actions[], evidence_index[], generated_at, as_of,
data_class, display_label
```

每条报告结论至少关联一项证据；重点结论建议至少有两个独立来源，或“一个公开来源 + 一段结构化轨迹”。

## 五、PRD 场景 2：关键设施持续监测

本轮不处理影像平台和 4 张自制图片。场景 2 先准备设施主数据、运行基线、状态记录、变化事件和报告结构；未来接入影像平台时再补影像资产及检测结果。

`monitoring_aoi.geojson`：

### 5.2 基线和状态记录

`facility_baseline.json`：

### 6.2 已经可以直接复用的内容

- 新闻的标题、摘要、地点、经纬度、标签和原始内容，可作为清洗输入。
- AIS 的 MMSI、船名、时间、经纬度、航速、航向和航行状态，可作为轨迹输入。
- ADS-B 的 ICAO 标识、机型、时间、位置、高度和速度，可作为航迹输入。
- 基地、机场、港口、装备和组织资料，可用于实体卡片和别名库。
- 海岸线、领海、毗连区、EEZ 和公海边界，可作为通用地理底图。
- 行为分析表可作为规则梳理起点，但需要工程化和校准后才能产出正式结果。

### 6.3 当前不能声称已满足的内容

- 不能把 59 条 AIS 或 28 条 ADS-B 离散记录称为连续监测数据。
- 不能把多个媒体名称写在一起的新闻算作多个独立来源。
- 不能把规则表中的置信度示例当作已验证的模型结果。
- 不能把装备百科数据当作对象当前部署、实时状态或活动证据。
- 不能用设施点位和介绍替代 PRD 场景 2 的设施基线、组成、变化和影响数据。

## 九、数据验收清单

交付前逐项检查：

- [ ] 三个场景均有固定 `scenario_id`、时间窗、对象范围和 `as_of`。
- [ ] 所有记录 ID 唯一，跨文件引用不存在断链。
- [ ] 新闻原文、翻译、摘要、来源、发布时间、采集时间和展示时间分开存储。
- [ ] AIS/ADS-B 原始观测与异常判断分开存储。
- [ ] 每艘船、每架飞机、每个设施都能关联到唯一实体。
- [ ] 所有时空字段统一为 UTC 和 WGS84。
- [ ] 同源转载已归组，不作为独立来源重复计权。
- [ ] 每项置信度都有来源、规则或人工判断说明。
- [ ] 每条报告结论都能回溯到具体证据记录。
- [ ] `REAL_FROZEN`、`DERIVED_SAMPLE`、`SIMULATED` 等属性在页面上可识别。
- [ ] 所有交付文件均记录 SHA-256、结构版本和已知限制。
- [ ] 对外展示已执行坐标精度、时间延迟和敏感对象范围检查。

## 十、数据团队的实际工作顺序

1. 先确定 PRD-S1 的一条事件和 PRD-S2 的一个设施，不要同时扩展多个故事线。
2. 给现有 25 条新闻、59 条 AIS、28 条 ADS-B 和相关设施记录补统一 ID 与溯源字段。
3. 完成实体消歧，建立新闻、轨迹、设施到实体的关联。
4. 补齐选定事件的连续轨迹、独立来源和异常结果。
5. 生成事件、主张、证据、核验矩阵、风险评估和报告。
6. 补齐设施范围、组成、基线、状态变化、影响和监测任务。
7. 最后再扩充美伊专题四类数据量，并校验卡片、趋势、列表和详情统计一致。

按这个顺序准备，可以先形成两个可完整讲清楚的闭环，再扩充数据规模；反过来只增加新闻、百科和图片数量，不会解决当前演示中“数据很多但结论串不起来”的问题。
