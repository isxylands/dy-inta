# 本机 Python 环境收敛评估与建议

> 评估日期：2026-08-08
>
> 评估范围：本机 4 套非 Codex Python、相关 Shell 入口、Homebrew 依赖、项目虚拟环境与主要缓存
>
> 当前状态：**仅完成只读取证和方案设计，未卸载 Python、未修改 PATH、未安装或删除任何包**

## 1. 结论

可以把日常需要用户主动选择和维护的 Python 收敛为 **1 套**，但不应把“只维护一套”误解成“磁盘上物理只剩一个 Python”。

推荐目标状态如下：

1. **唯一用户默认开发解释器：保留 pyenv 3.11.7。** 当前 `crawl4ai 0.9.2` 已安装并通过 `pip check`，13 个现有项目虚拟环境也以它为基础，立即替换的迁移成本最高。
2. **Homebrew Python 3.14.3：保留，但只作为 Homebrew 工具内部依赖。** 它由 `poetry` 和 `yt-dlp` 依赖，不能在保留这两个工具的同时单独删除。
3. **macOS Command Line Tools（CLT）Python 3.9.6：保留，但不作为开发环境。** 它属于 Apple 开发工具链，不能和用户 Python“合并”，也不值得为了约 24 MB 拆掉整个 CLT。
4. **Python.org Framework 3.7.2：建议在完成遗留任务确认后退役。** 它已停止上游支持，是 x86_64 解释器，当前不在 PATH 中；解释器及用户包合计约 429 MB。不过 2025-03 仍有包安装痕迹，不能仅凭“当前没进程”直接删除。
5. **统一命令入口比删除解释器优先。** 当前 `python`/`pip` 指向 pyenv 3.11，而 `python3`/`pip3` 指向 Homebrew 3.14；这是误装依赖和脚本行为漂移的直接风险。后续应让 pyenv shims 在交互式 Shell 的 PATH 中稳定排在 Homebrew 前面。

因此，推荐的稳态并不是物理 1 套，而是：

```text
用户直接维护：      pyenv 3.11.7                         1 套
包管理器内部维护：  Homebrew Python 3.14                不作为开发入口
操作系统工具链维护：CLT Python 3.9                      不作为开发入口
计划退役：          Python.org 3.7                      通过验证后删除
排除在本方案外：    Codex bundled Python                不动
```

从用户日常使用和维护责任看，这已经是“一套 Python”；从物理文件看，Homebrew 和 Apple 仍会各保留自己的运行时。

## 2. 目标、非目标与判断口径

### 2.1 目标

- 减少日常需要关注的 Python 版本和命令入口。
- 避免 `python`、`python3`、`pip`、`pip3` 指向不同环境。
- 在不破坏 Homebrew 工具、Apple 开发工具链和现有项目的前提下释放可回收空间。
- 给出可验证、可回滚的后续实施步骤，本轮不执行实施。

### 2.2 非目标

- 不修改 Codex bundled runtime。
- 不在本轮删除解释器、虚拟环境、缓存或浏览器。
- 不修改其他项目的 `.python-version`、`pyproject.toml` 或依赖锁文件。
- 不承诺所有 Python 项目共用一份全局 `site-packages`。解释器可以统一，项目依赖仍需隔离。

### 2.3 关键概念校正

“Python 环境”至少包含三层，不能混算：

| 层级 | 示例 | 是否适合合并 |
| --- | --- | --- |
| 基础解释器 | pyenv 3.11、Homebrew 3.14、CLT 3.9、Python.org 3.7 | 可退役冗余的用户解释器；不能合并工具链自带运行时 |
| 全局/用户级包目录 | pyenv `site-packages`、`~/Library/Python/3.7/...` | 不能跨 Python ABI 和 CPU 架构直接复制 |
| 项目虚拟环境 | 项目下 `.venv`、`venv` | 应按项目重建，不应汇总成一个全局包环境 |

本机 Python.org 3.7 是 x86_64，而 pyenv 3.11 和 Homebrew 3.14 是 arm64；其中 `numpy`、`lxml`、`pandas` 等包含原生扩展，不能把 3.7 的目录直接搬进 3.11。

## 3. 取证方法与边界

本次按“事实—假设—方案—验证—回滚”展开，主要完成了以下只读检查：

- 解释器解析：`command -v`、`type -a`、`sys.executable`、`sys.prefix`、`sys.base_prefix`。
- 版本和架构：`platform.python_version()`、`platform.machine()`、`file`。
- 安装归属：pyenv 版本清单、Homebrew `INSTALL_RECEIPT.json`、`xcode-select -p`。
- 依赖和健康度：`importlib.metadata`、`pip list`、pyenv 3.11 的 `pip check`。
- 空间：解释器、用户 `site-packages`、项目虚拟环境、`uv`、Homebrew 和 Playwright 缓存的 `du`。
- 引用：三个主要代码根目录、常用个人脚本目录和可读的 LaunchAgent/LaunchDaemon 配置中的硬编码解释器路径。
- 运行中占用：对四个解释器二进制执行 `lsof` 检查。
- 官方生命周期和工具行为：Python、Homebrew、pyenv、uv 官方资料。

边界与限制：

- 当前 PATH 是 Codex 会话观察值，不能替代 Terminal、Warp、IDE、定时任务等所有启动方式的现场验证。
- 没有发现硬编码引用或运行中进程，不等于从未有人手工调用 Python 3.7。
- 部分系统 LaunchDaemon 无读取权限；本轮未提升权限，也未做全盘内容扫描。
- `du` 是目录占用估算；缓存采用 clone、hardlink 或 APFS Copy-on-Write 时，最终可释放空间可能低于目录显示值。

## 4. 已确认事实

### 4.1 四套非 Codex 基础解释器

| 环境 | 版本/架构 | 当前入口与归属 | 解释器及包占用 | 关联项目虚拟环境 | 结论 |
| --- | --- | --- | ---: | ---: | --- |
| pyenv | 3.11.7 / arm64 | `python`、`pip`；用户管理 | 836 MB，其中全局 `site-packages` 606 MB | 13 个，合计 5.40 GiB | **保留为唯一默认开发解释器** |
| Homebrew | 3.14.3 / arm64 | `python3`、`pip3`；Homebrew 依赖 | Cellar 88 MB + 用户包 2 MB | 3 个，合计 0.15 GiB | **保留，但退出默认开发入口** |
| Apple CLT | 3.9.6 / universal | `/usr/bin/python3` 实际落到 CLT | 24 MB | 3 个，合计 0.23 GiB | **保留，仅供工具链/遗留 venv** |
| Python.org Framework | 3.7.2 / x86_64 | 不在 PATH；独立 Framework | Framework 191 MB + 用户包 238 MB | 未发现以它为基础且仍在扫描范围内的 venv | **验证后退役** |

四套解释器相关目录合计约 **1.35 GiB**。如果按推荐方案只退役 Python.org 3.7，理论上可释放约 **429 MB**，实际值以删除后的文件系统统计为准。

### 4.2 当前命令入口已经分裂

```text
python      -> /Users/liushen/.pyenv/shims/python        -> Python 3.11.7
pip         -> /Users/liushen/.pyenv/shims/pip           -> Python 3.11
python3     -> /opt/homebrew/bin/python3                 -> Python 3.14.3
pip3        -> /opt/homebrew/bin/pip3                    -> Python 3.14
```

观察到的 PATH 中 `/opt/homebrew/bin` 位于 pyenv shims 之前。Homebrew 在 `bin` 中提供 `python3`/`pip3`，但把无版本名的 `python`/`pip` 放在另一个 `libexec/bin` 目录，所以同一个 Shell 中恰好形成两套入口。

直接风险：

- `python -m pip install ...` 和 `python3 -m pip install ...` 会写入不同环境。
- 脚本只把 `python` 改成 `python3`，运行版本会从 3.11 跳到 3.14。
- 项目 `.python-version` 只能控制命中 pyenv shim 的命令；当前 `python3` 先被 Homebrew 截获，可能绕过 pyenv。
- 排查依赖问题时，裸 `pip`/`pip3` 输出容易被误认为属于同一个解释器。

### 4.3 pyenv 3.11 是当前迁移成本最低的保留对象

已确认：

- pyenv 当前只安装 `3.11.7`，global 也是 `3.11.7`。
- 全局共有 94 个 distribution，包含 `crawl4ai 0.9.2`。
- `python -m pip check` 返回 `No broken requirements found.`。
- `tools/feishu-doc-crawler` 要求 Python `>=3.11`；根脚本当前优先使用能导入 `crawl4ai` 的 `python`，并回退到 pyenv 3.11.7。
- 19 个扫描到的项目虚拟环境中，13 个的 `sys.base_prefix` 指向 pyenv 3.11.7，合计约 5.40 GiB。

这意味着现在删除或替换 pyenv 3.11，不只是释放 836 MB，还会使 13 个现有虚拟环境失去基础解释器或至少需要逐个重建和回归。

Python 官方当前把 3.11 列为 security 状态，计划支持至 2027-10。它不是长期最终版本，但仍有时间安排一次受控升级，不需要为了“版本看起来旧”立即迁移。

### 4.4 Homebrew 3.14 不能单独删除

本机 Homebrew receipt 明确记录：

```text
installed_as_dependency = true
installed_on_request    = false
reverse dependents      = poetry 2.3.2, yt-dlp 2026.3.17
```

`poetry` 和 `yt-dlp` 各自在 Homebrew 管理的 `libexec` 环境中运行，并把 `python@3.14` 记录为运行依赖。Homebrew 官方说明：formula 声明的 Python 依赖必须保留，否则脚本、模块或原生绑定可能失效。

因此，若直接卸载 `python@3.14`：

- Homebrew 可能拒绝卸载、连带卸载依赖者，或在下次修复/升级时重新安装。
- 3 个以 3.14 为基础的项目虚拟环境需要重建。
- 实际只节省约 90 MB，却引入明显工具损坏风险。

### 4.5 CLT 3.9 不是一套应由用户维护的 Python

`/usr/bin/python3` 实际执行：

```text
/Library/Developer/CommandLineTools/usr/bin/python3
Python 3.9.6
```

其 Framework 约 24 MB，属于 `/Library/Developer/CommandLineTools`。虽然 Python 3.9 已在上游结束支持，但这里的生命周期由 Apple CLT 管理。正确策略是：

- 不用它安装日常项目包。
- 不把它设成默认开发解释器。
- 不为删除 24 MB 去破坏或手工裁剪 CLT。

当前有 3 个虚拟环境运行时的 `sys.base_prefix` 指向 CLT 3.9，合计约 0.23 GiB；其中一个 `pyvenv.cfg` 还保留已不存在的 Intel Homebrew 3.8 路径，但运行时已落到 CLT 3.9，说明这个环境存在历史漂移，后续应由所属项目单独重建，而不是继续当成可靠环境。

### 4.6 Python.org 3.7 是最明确的退役候选，但仍需确认遗留用途

支持退役的证据：

- Python 3.7 已于 2023-06-27 结束上游支持。
- 当前解释器是 x86_64，运行在 arm64 Mac 上需要兼容层。
- Framework bin 和 `~/Library/Python/3.7/bin` 都不在当前 PATH。
- 扫描三个主要代码根目录和常用个人脚本目录，没有发现指向该 Framework、`python3.7` 的有效硬编码运行入口。
- 对解释器二进制执行 `lsof`，未发现当前运行进程。
- 扫描范围内未发现以该 Framework 为基础的现存项目虚拟环境。

不能直接删除的反证和疑点：

- 3.7 环境共可见约 65 个唯一 distribution，其中 53 个来自用户目录。
- 用户包包含 `openai`、`fastapi`、`pandas`、`numpy`、`lxml`、`python-docx`、`openpyxl`、`pyvmomi`、`itchat` 等，说明它曾承担多类脚本任务。
- 最新一批用户包文件时间为 2025-03-08，虽然已超过一年，但不能证明业务已经废弃。
- `~/Library/Python/3.7/bin` 仍有 `openai`、`httpx`、`tldr`、`pyvim` 等脚本，只是当前不在 PATH。
- 未验证 IDE 自定义解释器、手工绝对路径调用、不可读系统任务和外接脚本。

判断：**高概率可以退役，当前证据尚不足以授权立即删除。**

### 4.7 磁盘大头并不只在四个基础解释器

| 对象 | 当前目录占用 | 与“合并解释器”的关系 | 建议 |
| --- | ---: | --- | --- |
| 19 个项目 `.venv`/`venv` | 5.79 GiB | 项目生成环境，不是基础解释器 | 逐项目判断是否可重建/删除，不做全局清理 |
| `uv` cache | 3.3 GiB（3,593,359,360 bytes） | 下载、构建、`uvx` 等缓存 | 后续优先评估 `uv cache prune` |
| Playwright browsers | 1.5 GiB | 浏览器自动化运行时 | 先查使用者；不能因飞书适配器使用真实 Chrome 就推断全机都不需要 |
| Homebrew cache | 347 MB | Homebrew 下载/API 缓存 | 先执行 `brew cleanup -n` 估算，再决定清理 |
| pyenv 3.11 基础环境 | 836 MB | 推荐保留；606 MB 是全局包 | 不为省空间破坏当前 Crawl4AI 和 13 个 venv |
| Python.org 3.7 全部目录 | 429 MB | 明确退役候选 | 完成确认后删除 |

即使把 4 个基础解释器强行压到 1 个，能直接释放的解释器空间也远小于项目虚拟环境和缓存。优先级应是：先纠正入口与责任边界，再处理 EOL 解释器，最后按使用证据清理缓存和过期 venv。

## 5. 项目依赖现状

### 5.1 项目版本声明并不统一

本次找到 3 个 `.python-version`：

| 项目 | 声明 |
| --- | --- |
| `Shadowbroker` | `3.10` |
| `diting-mvp/apps/api` | `3.9` |
| `gintbroker` | `3.11` |

而 pyenv 当前只安装 3.11.7。项目的 `pyproject.toml` 多数写的是 `requires-python >=3.9` 或 `>=3.10`，但 `.python-version` 是本地工具选择的更具体约束。

这说明：

- “一个默认解释器”可以实现。
- “所有项目永远只允许一个 Python minor”需要逐项目修改版本声明并跑测试，当前没有证据支持直接这样做。
- 不能为了表面数量好看，顺手改掉其他项目的版本文件。

### 5.2 虚拟环境应视为可重建产物，而不是合并对象

扫描到的 19 个虚拟环境均能启动，但基础解释器分布为：

| 基础解释器 | venv 数量 | 目录合计 |
| --- | ---: | ---: |
| pyenv 3.11.7 | 13 | 5.40 GiB |
| Homebrew 3.14.3 | 3 | 0.15 GiB |
| CLT 3.9.6 | 3 | 0.23 GiB |

不建议把这些包全装进 pyenv 全局环境。不同项目可能要求不同版本的 `pydantic`、`numpy`、`openai` 等；合并后，一个项目升级包就可能破坏其他项目。

更合理的维护模型是：

```text
1 个默认基础解释器 + 每个活跃项目可重建的隔离依赖
```

虚拟环境不是需要人工逐包维护的“19 套 Python”；只要项目有 `pyproject.toml`/lock/requirements，它们应当可以通过 `uv sync`、`poetry install` 或项目规定命令重建。

## 7. 方案比较

| 方案 | 维护体验 | 直接空间收益 | 风险/代价 | 结论 |
| --- | --- | ---: | --- | --- |
| A. 物理只留 pyenv，删除 Homebrew/CLT/Python.org | 表面最少 | 约 543 MB | 破坏 `poetry`、`yt-dlp`、CLT；Homebrew 可能重新安装；多个 venv 失效 | **不推荐** |
| B. 1 个用户默认 pyenv + 保留工具链内部 Python + 退役 3.7 | 日常只维护 1 套，边界清楚 | 约 429 MB，另可独立清缓存 | 不追求物理数量为 1；需修正 PATH 并验证 3.7 遗留用途 | **推荐** |
| C. Homebrew 3.14 作为唯一开发 Python，删除 pyenv | 命令看似简单 | 基础环境约 836 MB | 13 个 venv/5.40 GiB 需重建；Crawl4AI 要迁移；Homebrew 默认版本会滚动且 base 为 externally managed | **当前不推荐** |
| D. 全面改用 uv 管理 Python 和项目环境 | 长期自动化较好 | 取决于重建和去重结果 | 当前项目 pin 不一致；可能自动下载多个 Python；迁移面大，现有 cache 已 3.3 GiB | **可作未来专项，不是本轮最小方案** |
| E. 同时保留 pyenv 3.11 和一个新版本 | 适合迁移窗口 | 稳态无收益 | 暂时增加一套，但能逐项目回归和回滚 | **仅作为未来升级过渡态** |

### 为什么不选择 Homebrew 3.14 作为唯一默认开发环境

它是当前最新支持线，但“版本新”不等于适合当统一基线：

- 本机安装它的原因是 Homebrew 工具依赖，不是项目选型。
- Homebrew 官方将 base 标记为 externally managed，要求项目包进入 venv。
- Homebrew 的 `python`/`python3` alias 会随默认 formula 演进，不适合要求独立生命周期或固定 patch 的项目。
- 本机最重的迁移成本在 pyenv 3.11 的 13 个 venv 和 Crawl4AI，而不是 3.14 本身。

### 为什么短期保留 3.11.7，而不是现在新装 3.12/3.13

本次目标是收敛，不是升级。现在先新增一个候选版本，会暂时增加环境数量；立即删除 3.11 又会同时触发 13 个 venv 重建。更稳妥的顺序是先把默认入口统一到已经验证可用的 3.11.7，等进入明确的 Python 生命周期升级窗口，再用“两版本短期并存—逐项目回归—删除旧版”的方式完成一次迁移。

## 8. 推荐实施路线（本轮未执行）

### 阶段 0：冻结基线和建立清单

目标：任何变更前都能回答“谁依赖哪个 Python”。

建议产物：

- 四个解释器的路径、版本、架构和目录大小快照。
- 每个解释器的 `pip freeze`，仅作恢复参考，不直接当跨版本锁文件使用。
- 19 个 venv 的项目、大小、`sys.base_prefix`、重建命令和负责人。
- Python 3.7 的用户脚本列表、IDE 解释器配置和定时任务检查结果。
- 高频命令验收清单：飞书抓取器、`poetry`、`yt-dlp`、主要项目测试命令。

退出条件：依赖清单可复核，且没有尚未确认归属的生产/定时任务。

### 阶段 1：先统一日常命令入口，不删除任何解释器

目标状态：新开的 zsh 中，以下四个命令都稳定命中 pyenv 3.11.7：

```text
python
python3
pip
pip3
```

建议动作：

1. 按 pyenv 官方方式在 zsh 启动文件中初始化 pyenv，确保 shims 位于 Homebrew `bin` 前。
2. 保留 Homebrew 自身路径；不要删除 `/opt/homebrew/bin/python3`，只是让交互式 Python 命令先命中 pyenv。
3. 项目和脚本统一使用 `python -m pip`，避免裸 `pip` 选错解释器。
4. 对必须使用 Homebrew Python 的诊断，显式调用 `/opt/homebrew/bin/python3`；不要靠临时调整 PATH 猜测。

验证：

```bash
command -v python python3 pip pip3
python --version
python3 --version
python -m pip --version
python3 -m pip --version
python -m pip check
poetry --version
yt-dlp --version
```

飞书抓取器至少执行单元测试、CLI 帮助和一次授权文档小样本抓取。涉及真实浏览器和远端数据时，应把输出写入临时目录，不提交抓取内容。

回滚：恢复修改前的 zsh 启动文件，重新打开 Shell；四个解释器目录都未删除，因此回滚不依赖重装。

### 阶段 2：退役 Python.org 3.7

前置条件：

- 完成 Python 3.7 `pip freeze`、用户脚本和绝对路径引用清单。
- 检查 Terminal/IDE/cron/LaunchAgent；对无法确认的手工任务完成使用者确认。
- 至少观察 14 天，没有发现 3.7 调用。
- 如果仍有遗留脚本，先迁移到独立、可重建的项目环境并完成结果对比。

删除范围必须精确限定为 Python 3.7 自身：

```text
/Library/Frameworks/Python.framework/Versions/3.7
/Users/liushen/Library/Python/3.7
```

实施时还应核对由原安装器创建的 3.7 专属 symlink/receipt；不能递归删除整个 `/Library/Frameworks/Python.framework`，也不能碰其他 minor。

验证：

- `python`/`python3` 仍命中 pyenv 3.11.7。
- `poetry`、`yt-dlp`、CLT 和飞书抓取器 smoke test 通过。
- 全局搜索不再出现指向已删除 3.7 Framework 的有效 shebang。
- 对比实施前后的磁盘可用空间。

回滚：优先从实施前的文件级快照恢复；否则重装兼容的 Python 3.7，并按保存的依赖清单重建。因为 3.7 已 EOL，回滚只用于短期恢复遗留任务，随后仍应迁移而不是继续把它作为默认环境。

### 阶段 3：独立处理缓存和过期虚拟环境

这一步比继续删除工具链 Python 更可能释放明显空间，但必须与解释器收敛分开审批。

1. `uv`：先使用官方的 `uv cache prune`，不要手工删除 cache 子目录。`uv cache clean` 会删除更多可重建项，只有在确认 `uvx`/集中项目环境影响后再考虑。
2. Homebrew：先执行 `brew cleanup -n` 查看预计删除项，再决定是否正式 cleanup。
3. Playwright：先确认哪些项目需要缓存浏览器，再使用 Playwright 自身卸载/安装命令；不要直接 `rm` 整个目录。
4. 项目 venv：只删除已确认不再使用、且依赖锁和重建命令完整的环境。两个隐私检测 venv 合计已超过 3.8 GiB，应由所属项目优先确认。

回滚原则：缓存通过工具自动重建；项目 venv 从 lock/requirements 重建。没有可复现依赖声明的 venv 不应先删。

### 阶段 4：在 Python 3.11 生命周期到期前做一次受控升级

建议在 2027-10 前留出迁移窗口，而不是等到 EOL 当天：

1. 用 pyenv 安装一个候选支持版本，短期与 3.11.7 并存。
2. 先验证 Crawl4AI、飞书适配器和含原生扩展的依赖。
3. 按项目重建 13 个 venv，运行各自测试和真实关键流程。
4. 搜索所有 `sys.base_prefix`、shebang 和配置，确认不再引用 3.11.7。
5. 再通过 `pyenv uninstall` 删除旧版本；不要手工删除目录绕过 pyenv 插件逻辑。

候选版本不能只按 `requires-python` 元数据决定。元数据只说明解析范围，不证明本机 arm64 wheel、浏览器驱动和真实抓取链路都兼容。

## 9. 验收矩阵

| 验收项 | 通过标准 | 失败处置 |
| --- | --- | --- |
| 默认入口一致 | `python`、`python3`、`pip`、`pip3` 均属于同一 pyenv 版本 | 立即回滚 Shell 配置 |
| pyenv 包完整 | `python -m pip check` 通过，Crawl4AI 可导入 | 不执行下一阶段，恢复依赖 |
| 飞书适配器 | 单测、CLI、小样本抓取和完整性报告通过 | 保留旧入口，定位浏览器/依赖差异 |
| Homebrew 工具 | `poetry --version`、`yt-dlp --version` 和最小功能正常 | 恢复 PATH；核对 Homebrew libexec |
| Apple 工具链 | 常用编译、Git/CLI 流程正常 | 不删除/修改 CLT，恢复启动配置 |
| Python 3.7 退役 | 无任务、shebang、IDE 或 venv 引用；关键业务无回归 | 从快照/安装介质恢复，迁移遗留任务 |
| 磁盘收益 | `df` 和目标目录 `du` 与预估方向一致 | 检查 APFS clone/hardlink，不继续盲删 |
| 项目环境 | 每个被重建项目的测试和启动命令通过 | 单项目回滚原 venv，不扩大影响面 |

## 10. 风险与防护

### 高风险：误删工具链运行时

- 风险：将 Homebrew/CLT Python 当成普通用户 Python 删除。
- 防护：只使用所属包管理器处理；Homebrew 先看反向依赖，CLT 不做目录级裁剪。

### 高风险：跨版本复制 site-packages

- 风险：Python ABI、arm64/x86_64 和原生扩展不兼容，产生导入崩溃或隐性错误。
- 防护：从声明文件重新解析和安装，只把 `pip freeze` 当迁移参考。

### 中风险：统一 PATH 改变脚本默认版本

- 风险：以前依赖 `python3`=3.14 的脚本会转到 3.11。
- 防护：先搜索 shebang/启动脚本；对确需 3.14 的工具使用其 venv 或绝对路径；分 Terminal、IDE、自动任务验证。

### 中风险：删除 pyenv 3.11 破坏 13 个 venv

- 风险：虚拟环境的基础解释器消失，5.40 GiB 项目环境需要重建。
- 防护：短期保留 3.11；升级时以 `sys.base_prefix` 清零旧引用作为删除门槛。

### 中风险：把目录大小当成可释放空间

- 风险：APFS clone、hardlink 和工具缓存复用会造成 `du` 与真实释放量不同。
- 防护：用工具自己的 prune/cleanup，前后同时记录 `du` 和 `df`。

## 11. 最终建议

按风险、收益和维护成本排序：

1. **先统一 `python`/`python3`/`pip`/`pip3` 到 pyenv 3.11.7。** 这是最有价值且可快速回滚的治理动作。
2. **保留 Homebrew 3.14 和 CLT 3.9，但从用户心智中移出。** 它们由各自工具链维护，不计入“用户要维护几套”。
3. **验证后退役 Python.org 3.7，预计释放约 429 MB。** 先处理最近一次使用和遗留任务疑点。
4. **空间优化另开清理批次。** 优先看 `uv` 3.3 GiB、Playwright 1.5 GiB、项目 venv 5.79 GiB，而不是冒险删除 24–90 MB 的工具链 Python。
5. **不要建立一个全局包大杂烩。** 目标应是一个默认基础解释器，项目依赖通过 lock + venv 可重建；这才是真正降低维护成本。
6. **Python 3.11 升级作为后续生命周期任务。** 允许短期两版本并存，逐项目验证后再删除旧版；不在本次收敛中同时做大版本迁移。
