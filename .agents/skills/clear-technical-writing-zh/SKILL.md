# 中文技术写作

让读者看懂内容、找到所需信息，并据此讨论、实施或验收。按材料用途判断写法，不把技术材料统一改成论证文章。

项目方案、总体设计、技术方案、建设方案和系统设计说明正文改由 `project-solution-doc-writer` 处理；即使用户只说“润色”“去 AI 味”或“改得更具体”，只要对象是方案类正文，也应优先使用该 skill。本 skill 仍可处理 README、指南、需求规格、技术报告、通用论证、交接说明和非方案类材料。

## 先确定本次怎么写

以用户指定的基准稿、读者、文种和修改范围为准，保留已确认的术语、目录、编号与技术含义。有版本对比任务或需要承接用户修改时才比较历史稿；局部润色不必重建全文骨架。

按读者的任务决定解释深度。简单问题直接回答；复杂材料展开影响理解、判断、操作和验收的细节，不按固定字数或条目数裁剪。常见技术概念不从头科普；小众、多义或容易误解的术语首次出现时说明本文含义，必要时补英文全称。

摘要、论证结论和设计取舍已有明确判断时，先说判断，再给关键依据、约束和实际影响。需求条目、接口说明和操作步骤仍按查找与执行所需的顺序展开，不为制造结论句打乱规则。

同一文档的不同章节可以采用不同写法。下表用于选择表达重点，不是要求补齐的目录：

| 材料或章节 | 读者需要得到的信息 | 合适的表达 |
| --- | --- | --- |
| 通用论证或非方案类项目说明 | 问题背景、现状条件、处理选择、范围和实施安排 | 从实际需求说明选择依据；概述、功能清单和技术专题各有用途 |
| 技术研究、论证 | 问题与难点、拟用方法、依据及验证思路 | 把研究问题与处理方法讲清楚，区分已有基础和待验证设想 |
| 非方案类局部设计说明 | 系统组成、职责分配、关键流程、接口与部署关系 | 先说明整体关系，再分层展开；按需分别组织架构、数据和功能视图。项目总体设计正文改用 `project-solution-doc-writer` |
| 接口与局部实现说明 | 实现所需的处理逻辑、数据结构、接口契约及异常行为 | 使用步骤、表格、伪代码或段落表达具体规则，不为行文流畅删去条件 |
| 需求规格说明 | 用户或系统在什么条件下应有何种行为，如何判断满足 | 保留需求编号、条目、约束和验收条件；“应”“必须”“不得”可用于规范性要求 |

## 首稿先建立内容主线

起草整篇材料或主要章节前，先从已有材料中理清：谁在什么业务过程中遇到什么问题，重点和困难在哪里，哪些条件限制了解决办法，拟采取或已经采取什么处理，处理后发生什么变化。正文沿这些关系展开，再按文种安排章节；不要先罗列平台、能力和技术名词，再补写它们的重要性。这是构思依据，不是固定目录；接口说明、数据字典和局部设计可直接写具体规则，不必重讲业务背景。

关键设计用有来源的业务过程、对象、输入输出、操作条件或前后变化解释，说明当前条件下为什么这样做、解决到什么程度、仍受什么限制。技术名称和功能清单用于定位，不能代替处理过程与选择依据；展开深度服从文种。成熟功能不必制造技术难点，后续改进只写与当前限制或已明确需求有关的内容，不机械附加未来规划。

同一主题跨章节出现时，让信息逐层深入：需求说明目标行为，设计解释组成和协作，技术论证解释关键困难与选择，验证说明结果和限制。这些是信息分工，不要求章节一一对应。共同前提在合适位置讲清，后文简要承接并补充本章的新判断，不把每节写成重新介绍定位、价值和全套能力的独立文章。

## 成组整理项目文档

用户要求整理 README、指南、报告等多份文档时，先核对各份材料的用途、适用版本和事实来源，再决定保留什么、放在哪里。README 说明项目和最短上手路径，详细操作进入指南；规格与设计保留可实施的规则，验证报告记录对应版本的实测结果。沿用项目现有分工，不为统一目录重复搬运内容。

对易变化的事实确定一个可核对的详细来源，其他位置只保留本处阅读所需的摘要，并给出具体链接。字段、默认值和限制由代码、配置或实际产物决定时，先核对再引用相应文件、符号或产物；临时路径、单次运行状态和动态数量在当次记录中标明日期或版本，长期指南说明查询方法。设计讨论、尝试和历史进度放在过程记录；正式指南说明当前有效的用法，历史报告标明所述版本和依据。

## 保住内容，再改表达

- **不以润色改变事实。** 保留条件、数值、责任主体、否定、例外和不确定性；不能把拟议方案写成已实现，也不能把建议改成自动执行。涉及效果时区分设计目标、推测收益和已验证结果，不把完成某个流程写成效果必然成立的保证。来源缺口应指出或列为待确认，不能靠虚构场景、算法、接口或指标显得具体。
- **用文档作者的口吻写正式内容。** 直接说明功能、规则、决定和结果，不把“按用户要求”“已获授权”“本轮完成”等助手对话、编辑过程或自我汇报写进正文。确认记录本身若是重要依据，写清主体、时间和来源；过程材料可以记录过程，不冒充当前能力。
- **限制写具体。** 把失败结果、测量条件、适用范围和必要操作要求放在相关结论旁边，删去没有新增信息的反复免责声明。保留必要的安全与法律说明、许可证原文和第三方归属，不因追求简洁抹去事实边界。
- **技术关系清楚即可，不强迫每段写全。** 需要时说明谁处理什么、交给谁、产生什么结果。主语明确时可用“系统”“该模块”；多个主体容易混淆时再点名。沿用来源的职责划分，不套用样例中的组件关系。
- **术语准确且一致。** 专业概念在需要消歧时解释。同一对象保持同一名称，不为降低词频改用近义词；不同对象也不能因追求统一而混称。
- **先删空话，再改句子。** 删除重复判断、空泛评价和读者已掌握的背景，再合并共同前提。保留条件、数值、责任、例外、接口字段和操作步骤；需求与设计的对应关系、必要概述和查阅入口按用途保留。多个主体、条件或转折使句子难读时拆句，不靠删限定语缩短。

## 让形式服务于阅读

段落解释原因和关系，列表列出并列要求或步骤，表格便于逐项比较，图展示结构与流向。按内容选择，不限定每节段数、每段句数，也不要求各小节完全对称。图名应反映图的实际内容，不能只改名称就把功能架构变成技术研究。

没有落点的评价应回到具体处理与结果；已有准确技术含义的“闭环”“端到端”等术语可以保留。

直接说判断，再给必要依据；对照用于真实差异或误解，删除否定前半句若不损失含义，就只写后半句。“仍然、再次”需要已有状态，“反而、却”需要合理预期，“其实、真正、本质上”需要确切的纠偏或层次依据。没有这些前提就删去，不建立禁词表。“首先、其次”可表达步骤，“本文档……”可交代用途；少量排比和概括句有信息承接时可以保留。

需要对齐正向样例，或难以判断该保留还是改写时，阅读 [样例与取舍](references/positive-examples.md)。学习其组织方式和信息展开，不照搬技术选型、业务事实或全部文风。

## 完稿检查

对照任务和原文通读一次：原意、承诺和关键细节是否保留，读者能否理解处理过程、找到操作规则、判断依据与限度？每段应推进判断、解释机制、指导操作或说明边界；无此作用的铺垫和重复删除。缺少依据时指出具体缺口，不用套话补齐。内容完整就结束，不再复述全文，不靠自评分数或短语计数验收。

成组整理项目文档时，核对相关模板、生成器、示例和分发副本，避免后续生成恢复旧内容；检查链接、锚点、代码引用、命令示例及其适用版本。在本次授权范围内同步修正文本来源和副本；超出范围的不一致应指出，不为修正文案改变程序行为。

编辑 Word 等文件时保留约定样式和编号，按相应文件技能检查版式。
